## 1. Unreal Engine 5.x 세부 버전

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **UE 5.4** | 안정 · 자료·플러그인 풍부 · LTS에 가까움 | 최신 기능 일부 부재 |
| **UE 5.5** | 비교적 최신 · 개선 다수 | 플러그인 호환 확인 필요 |
| **UE 5.6+ (최신)** | 최신 기능 | 변경 빈도·학습 비용 · 팀/에셋 재현성 리스크 |

### 권장안

**UE 5.4** (또는 설치 환경에서 확보 가능한 **5.4.x 최신 패치**).

### 결정 근거

- 1인·소규모 · 메카 액션 · Enhanced Input / Niagara / UMG / BT는 5.4로 충분.
- 버전 고정이 에셋·재현성에 유리. 최신 추적보다 VS 완성이 우선.
- 이후 메이저 업은 VS 이후 검토.

### 구현에 미치는 영향

- 프로젝트 생성 시 엔진 버전 고정.
- 파이프라인 G2 (UE 버전) 해소.

## 2. VS 보스 — 세스 vs 몬투

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **세스 (EP6)** | 1:1 보스 긴장 · 씰/차단 기믹 명확 · VS_EP1_6_8 핵심 축 · HP 480 · 스펙 풍부 | 전투 4–7분 · 기믹 구현량 상대적 큼 |
| **몬투 (EP5)** | HP 360 · 시간 짧음(3–5분) · 공간 압박 단순 · 학습→왜곡 구조 명확 | EP1–6–8 삼각 중 EP6 축이 약해짐 · 세스만큼 스토리 애착 축 아님 |

### 권장안

**세스 (COLOSSUS / EP6)** 를 VS 보스로 한다.

### 결정 근거

- 기존 Vertical Slice 잠금이 **EP1 · EP6 · EP8** 삼각. EP6이 빠지면 “1:1 보스 긴장” 검증이 약해짐.
- 세스 스킬·페이즈·클리어 연출이 문서화되어 있음.
- 몬투는 두 번째 보스 또는 잡몹 다음 단계 검증용으로 유지.

### 구현에 미치는 영향

- Phase 머신 + 씰/차단 패턴 1세트가 VS 범위에 포함.
- ASSET_REGISTER 보스 우선순위 세스 = VS 확정.

## 3. 타깃 플랫폼 / 개발 하드웨어

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **PC (Windows) only** | 개발·디버그 단순 · 1인 적합 | 콘솔 이슈 나중에 |
| PC + 콘솔 동시 | 이식성 조기 확보 | 입력·퍼포·인증 비용 |

### 권장안

- **출시/검증 타깃:** PC (Windows) 우선.
- **개발 하드웨어:** 중상급 PC (권장 최소 가이드만, 벤치마크는 P1).
  - CPU: 현대 6코어급 이상
  - GPU: RTX 3060급 이상 (제안)
  - RAM: 32GB 권장
- 콘솔·Switch 패드는 **입력 매핑 설계 참고**만 (08_PLAY_BRAVE). 빌드 타깃 아님.

### 결정 근거

- Charter·기존 문서가 PC/언리얼 중심.
- VS 단계에서 멀티 플랫폼은 범위 과다.

### 구현에 미치는 영향

- 프로젝트 타깃: Win64.
- 입력: Enhanced Input · 패드+KBM.

## 4. 목표 FPS

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **60 FPS** | 히트스톱·대시 12f 등 기존 프레임 설계와 정합 · 액션 손맛 | 고부하 시 유지 필요 |
| 30 FPS | 여유 | 대시/경직 체감 둔화 · 기존 12f 환산 재작업 |
| 120+ 가변 | 고주사율 | 튜닝 복잡도 · VS 불필요 |

### 권장안

**목표 60 FPS** · 가변 프레임 · 하한 모니터링은 P1.

### 결정 근거

- 대시 무적 ~12f · 히트스톱은 60 전제 초안과 맞춤이 자연스러움.
- TECHNICAL_REQUIREMENTS 제안과 동일.

### 구현에 미치는 영향

- 타이머·애니는 실시간(초) 또는 60 기준 프레임으로 통일해 문서화.
- 고정 30 강제 비사용.

## 5. Root Motion 정책

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **(A) In-place + CharacterMovement** | 이동 로직 코드 일관 · 대시/콤보 조정 용이 · 파이프라인 제안과 일치 | 일부 시네마틱 이동은 별도 처리 |
| **(B) Root Motion 곡선 사용** | 애니 기반 이동 정확 | 네트워크·보정·콤보 중 루트 충돌 복잡도 |

### 권장안

**(A) In-place 클립 + CharacterMovement (코드 이동)**.

필살·연출 일부만 제한적 Root Motion 또는 시퀀서 검토 (VS 이후).

### 결정 근거

- MESHY_BLENDER_PIPELINE_SPEC 권장 1차와 동일.
- 메카 액션·대시 쿨·콤보는 코드 측 제어가 튜닝에 유리.

### 구현에 미치는 영향

- 애니 익스포트: in-place.
- Movement Component가 속도·대시 거리 소유.

## 6. 애니메이션 FPS

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **30 fps** | 용량·제작 부담 적음 · 많은 게임 관례 | 빠른 콤보 시 보간 의존 |
| **60 fps** | 타격 타이밍 세밀 | 키 수·용량 증가 |

### 권장안

**제작·익스포트 기준 30 fps**.

게임 타깃 60과 별개. UE 샘플링/보간으로 재생. 타격 판정은 Notify 시간(초) 기준.

### 결정 근거

- 1인 파이프라인·Blender 작업량.
- 판정은 프레임 번호 하드코딩보다 시간/Notify가 안전.
- 필요 시 특정 클립만 60 제작 가능 (예외).

### 구현에 미치는 영향

- 파이프라인 G6 해소 방향.
- 문서의 “12f” 등은 **60Hz 기준 프레임**으로 해석하거나 초 단위로 병기.

## 7. Skeleton / Bone Naming 규칙

### 선택지 비교

| 선택 | 장점 | 단점 |
|------|------|------|
| **UE Mannequin 호환 이름** | IK·리타깃·예시 자료 풍부 | 메카 전용 소켓 추가 필요 |
| **완전 커스텀 PascalCase** | 메카 의미 명확 | 리타깃·마켓 애셋 연동 비용 |
| **snake_case** | 일부 DCC 관례 | UE 기본 예시와 불일치 |

### 권장안

**UE 친화적 PascalCase + L_/R_ 접두** · 최소 계층은 파이프라인 스펙 제안을 채택하고 이름을 아래에 고정.

```
Root
└─ Pelvis
   ├─ Spine
   │  └─ Chest
   │     ├─ Neck → Head
   │     ├─ Clavicle_L → UpperArm_L → LowerArm_L → Hand_L
   │     └─ Clavicle_R → UpperArm_R → LowerArm_R → Hand_R
   ├─ UpperLeg_L → LowerLeg_L → Foot_L
   └─ UpperLeg_R → LowerLeg_R → Foot_R
```

- ASCII only · 공백 없음
- Deform 본만 익스포트
- 무기/드론: `Socket_Weapon_R` 등 `Socket_` 접두 (추가 본)
- IK 컨트롤 본은 FBX 제외 (파이프라인 LOCK 의도)

Mannequin과 1:1 동일할 필요는 없으나, 리타깃 가능성을 위해 인간형 대칭 계층 유지.

### 결정 근거

- MESHY_BLENDER_PIPELINE_SPEC §5 제안과 정합.
- 다기체 Skeleton 공유 목표에 유리.

### 구현에 미치는 영향

- G3 (본 이름 최종 표) 초안 확정.
- Blender 리그·FBX·UE Skeleton 생성 시 동일 표 사용.
