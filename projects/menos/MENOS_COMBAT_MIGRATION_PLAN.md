제거 또는 비활성화할 것:
- 플레이어가 Tower Defense 운영을 계속해야 하는 핵심 구조
- Robot을 자동으로 움직이게 하는 것이 기본이라는 전제
- Tower 업그레이드/배치가 전투의 핵심 의사결정이 되는 구조
- RTS식 아군 지휘
- 플레이어가 여러 로봇을 동시에 직접 조종하는 구조

## 4. 목표 런타임 구조

목표 전투 루프:

스테이지 진입 → 플레이어 로봇 조종 → 일반 적 다수전 → AI 아군 지원 → 고정형 시설 지원 → XP 획득/즉시 레벨업 → 특수무기/필살기 사용 → 거대 보스전 → 승리/패배

핵심 원칙:
- 플레이어는 항상 자기 로봇 1기를 직접 조종한다.
- 기본 이동은 직접 조작이 우선이다.
- 기본 공격은 플레이어 입력 또는 명확한 조준/타깃 입력으로 발동한다.
- 특수무기와 필살기는 플레이어가 직접 사용한다.
- AI 아군은 자동으로 싸우며 직접 명령하지 않는다.
- 지원 시설은 자동으로 작동한다.
- 적 웨이브는 전투 콘텐츠 공급 방식으로 남을 수 있지만 게임의 정체성이 웨이브 관리에 있지는 않다.

## 5. 조작 체계 전환

### 현재
- WASD/방향키 직접 이동이 이미 존재한다.
- Robot은 동시에 자동 이동/자동 타깃/자동 기본공격을 수행한다.
- 마우스 클릭은 Tower 선택/배치와 Robot 선택/이동에 사용된다.

### 목표
- 이동: WASD/방향키 기본
- 기본 공격: 명확한 입력 1개
- 특수무기: 액션 슬롯 기반 직접 입력
- 필살기: 별도 강력한 입력
- 타깃 선택: 클릭 또는 명확한 타깃 전환 입력
- 타깃 전환: 키보드 입력으로 빠른 전환
- 회피/방어: 별도 행동으로 설계 여부 검토

정확한 키 배치는 아직 Canon으로 확정하지 않는다. 먼저 입력 기능과 상태 전이를 분리하고, 키 매핑은 이후 별도 결정한다.

### 금지
- 기존 Tower UI 버튼을 그대로 액션 슬롯으로 이름만 바꾸는 방식
- 자동 전투를 유지한 채 플레이어 입력만 추가하는 방식
- LoL식 스킬 이름/구조를 그대로 복제하는 방식

## 6. Robot 전투 아키텍처 전환

현재 main.gd에 Robot 이동, 타깃, 공격, 특수공격, 성장, 렌더링 상태가 강하게 결합되어 있다.

1차 목표는 Robot 로직을 다음 책임으로 분리하는 것이다.
- 입력 상태
- 이동 상태
- 타깃 상태
- 기본 공격
- 특수무기
- 필살기
- 피격/파괴
- 성장
- 애니메이션 상태

처음부터 대규모 클래스로 재작성하지 않는다. 현재 코드 경로를 유지하면서 책임을 단계적으로 분리한다.

목표 상태 예:
IDLE / MOVE / ATTACK / SPECIAL / FINISHER / HIT / DESTROYED

자동 이동은 기본 행동에서 제거하고, 필요할 경우 AI 아군 또는 특정 NPC에만 재사용한다.

## 7. 공격 시스템 전환

현재 Robot 기본 공격은 주변/거리 기반 자동 타깃과 자동 투사체 생성이 중심이다.

목표는 "무기 사용" 중심으로 재구성한다.

예시 슬롯 구조:
- Basic Weapon
- Special Weapon 1
- Special Weapon 2
- Finisher

각 무기는 다음 데이터를 가진다.
- 입력
- 대상 방식
- 사거리
- 피해
- 범위/관통 여부
- 쿨다운 또는 에너지
- 애니메이션
- 투사체/효과
- 사용 가능 상태

실제 무기 목록과 수치는 아직 확정하지 않는다.
## 8. 타깃 시스템 전환

현재 타깃은 거리와 적 위치를 이용한 자동 선택 성격이 강하다.

목표:
- 현재 타깃을 HUD에서 명확하게 표시
- 마우스 클릭으로 타깃 지정 가능
- 타깃 전환 입력 제공
- 타깃이 없어도 이동과 비조준 공격은 가능
- 보스전에서는 특정 거대 적을 명확하게 고정할 수 있음
- 다수전에서는 빠른 타깃 전환이 가능

자동 타깃은 보조 기능으로 남길 수 있으나 플레이어 선택을 덮어쓰면 안 된다.

## 9. 다수전 / 보스전 공통화

같은 기본 조작으로 두 상황을 처리한다.

다수전:
- 이동으로 적 무리를 관통하거나 회피
- 범위/관통 무기 사용
- 타깃 전환
- 다수 적 처치로 XP 획득

보스전:
- 동일 이동
- 보스 타깃 고정
- 공격 패턴 회피
- 빈틈에 특수무기 사용
- 필살기 사용

보스 전용 조작을 별도로 만들지 않는다.

## 10. AI 아군 전환

현재 Canon에는 AI 아군이 확정되어 있지만 기존 PoC의 핵심 구조에는 충분히 독립된 아군 시스템이 없다.

따라서 AI 아군은 Robot 직접조종 전환이 안정된 뒤 별도 단계로 추가한다.

아군 원칙:
- 자동 이동
- 자동 타깃
- 자동 공격
- 플레이어의 명령/선택 없음
- 플레이어 Robot의 HUD와 구분

초기 구현에서는 1종 AI 아군만으로 구조를 검증한다. 여러 종류를 동시에 만들지 않는다.

## 11. Tower → 고정형 지원 시설 전환

Tower 시스템은 즉시 삭제하지 않는다.

현재의 배치/자동공격 구조를 다음과 같이 재정의한다.

- 설치: 스테이지가 지정하거나 제한된 위치에 배치
- 운영: 자동
- 직접 조작: 없음
- 업그레이드: 초기 전환에서는 우선순위 낮음
- 역할: 화력/방어막/수리/에너지/대공 등 지원

기존 Tower Editor와 content/towers/towers.json은 재사용 가능성을 우선 조사한다.

플레이어가 전투 중 Tower 버튼을 계속 눌러야 하는 구조는 제거한다.

Tower 설치가 캠페인 설계상 필요한지 여부는 별도 Master 판단으로 확정한다. Canon은 Tower를 삭제하지 않고 고정형 지원 시설로 정의했으므로, 현재 단계에서 Tower 시스템을 폐기하지 않는다.

## 12. HUD 전환

현재 HUD에는 Tower Defense와 Robot 직접조작 요소가 혼재한다.

목표 HUD 우선순위:
1. Robot HP
2. 에너지/특수 자원
3. 레벨/XP
4. 현재 타깃/타깃 HP
5. 기본 무기
6. 특수무기 슬롯
7. 필살기
8. 쿨다운/사용 조건
9. 전투 상황 정보

축소/후순위:
- GOLD
- Tower 구매 버튼
- Tower 업그레이드 버튼
- 기지 운영 정보의 과도한 노출
- Inventory를 전투 화면의 핵심 영역에 배치하는 것

기지 HP와 지원 시설 상태는 필요할 경우 보조 정보로 남긴다.

## 13. 성장 시스템 전환

현재 XP/레벨업 로직은 이미 전투 중 즉시 레벨업을 지원한다.

이 부분은 유지한다.

변경 대상은 레벨업 이후의 플레이어 선택 방식이다.
현재 웨이브 클리어 후 GROWTH 상태에서 능력을 선택하는 구조는 직접 조종 Canon과 충돌할 수 있으므로 재설계한다.

목표 방향:
- XP 충족 즉시 레벨업
- 전투 흐름은 가능한 한 유지
- 레벨업으로 새 무기/강화/전투 해결책 획득
- 플레이어가 직접 사용하는 행동과 연결

구체적인 레벨업 UI와 선택 여부는 별도 설계 후 구현한다.

## 14. Wave 시스템의 재정의

Wave 자체를 즉시 제거하지 않는다.

현재 스테이지 데이터와 적 스폰 시스템은 콘텐츠 공급에 유용하다.

다만 목표 구조에서는 Wave가 플레이어의 주된 게임플레이가 아니다.

따라서:
- 자동 웨이브 시작은 유지 가능
- 적 그룹/스폰 데이터는 재사용
- Wave Clear → 성장 선택 → 다음 Wave라는 경직된 루프는 완화
- 전투 중 계속 싸우는 흐름을 우선
- Boss는 단순히 마지막 Wave의 큰 적이 아니라 별도 전투 상황으로 취급

## 15. 맵 / 카메라 / 스테이지 데이터

Map과 Stage 구조는 최대한 보존한다.

유지 우선:
- 60x40 Campaign 1 기준
- 스크롤 카메라
- 스폰 위치
- 목표/기지 위치
- Robot 출격/시작 위치
- 타워 설치 영역 데이터는 지원 시설 영역으로 재사용 가능

변경 필요성이 높은 부분:
- Robot 전투 공간을 직접 조종에 맞게 재검토
- 자동 이동 경로보다 자유 이동 공간의 중요도 증가
- 보스전에서 충분한 전투 공간 확보

맵 데이터 자체를 먼저 대규모 수정하지 않는다. 조작 PoC가 성립한 뒤 필요한 최소 변경만 한다.

## 16. Editor 영향

현재 Editor 구성은 유지한다.

Map Editor:
- 플레이어 이동 공간
- 스폰/보스 위치
- 지원 시설 위치/영역을 다룰 수 있도록 확장 필요성이 있음

Stage Editor:
- Wave/적 그룹뿐 아니라 Boss 전투 구성 데이터를 담을 수 있어야 함

Enemy Editor:
- 적 이동/공격/보스 속성 확장

Tower Editor:
- Tower가 지원 시설로 전환될 경우 역할/자동작동 데이터 중심으로 재정의

Robot Editor:
- 직접조종에 필요한 이동/공격/특수/필살기 데이터 추가 필요
- 현재 애니메이션 미리보기 기능은 유지

Image Editor:
- 변경 없음

새 Editor를 바로 만들지 않는다. 기존 Editor가 새 데이터 구조를 표현할 수 없는 경우에만 추가한다.

## 17. Asset 전략

기존 Asset을 먼저 재사용한다.

우선순위:
1. 현재 Robot 스프라이트/애니메이션
2. 현재 투사체
3. 현재 적
4. 현재 배경/맵
5. 현재 Tower를 지원 시설로 재사용 가능한지 확인

새 Asset은 직접조종 전투에서 실제로 부족한 경우에만 만든다.

특히 초기 전환에서 새 로봇/새 적/새 맵을 동시에 제작하지 않는다.

- 기존 변경사항 보호
- 코드/Asset/Data의 실제 전환 대상 목록 확정

성공 조건: 무엇을 바꾸고 무엇을 보존할지 설명 가능.

### Phase 1 — Robot 직접조종 최소 전투

- Robot 선택/이동 명령과 Tower 클릭 충돌 제거

성공 조건: 플레이어가 Robot 1기로 적을 직접 움직이고 공격할 수 있음.

성공 조건: 다수전에서 의도한 적을 선택하고 공격 가능.

- 기존 special 로직을 직접 입력 구조로 전환

- 필살기 1종
- HUD 액션 슬롯 연결

성공 조건: 일반 공격과 특수무기의 플레이 방식이 구분됨.

성공 조건: Robot이 전투의 중심이고 지원 시설은 보조 역할로 기능함.

- Campaign 1 최소 전환

성공 조건: 최소 1개 캠페인 스테이지가 새 Canon으로 처음부터 끝까지 플레이 가능한 상태.

## 19. 단계별 검증 기준

각 Phase는 최소 검증 후 멈춘다.

CODE VERIFIED:
- 실제 입력/상태/피해 경로를 코드에서 확인

EDITOR VERIFIED:
- 관련 데이터와 Editor에서 실제 설정 가능 여부 확인

BUILD VERIFIED:
- 실제 실행 파일 생성 성공

PIE VERIFIED:
- Master가 실제 플레이 결과를 확인

자동화 테스트 PASS만으로 PIE VERIFIED를 선언하지 않는다.

## 20. 변경 안전성

모든 Phase 시작 전:
- HEAD 확인
- Branch 확인
- Working Tree 확인
- 기존 변경사항 목록화

변경 후:

- .godot 기존 변경은 건드리지 않음
- 대규모 Asset 변환 금지

각 Phase에서 목적과 직접 관계없는 문제는 OUT OF SCOPE로 남긴다.

## 21. 첫 구현에서 하지 않을 것

다음은 현재 migration 범위에서 자동 진행하지 않는다.
- 멀티플레이
- 온라인 협동
- 여러 플레이어 로봇 동시 조종
- 대규모 신규 Asset 제작
- 신규 맵 여러 개 제작
- 복잡한 인벤토리/루팅 시스템 확장
- 복잡한 RTS 아군 명령
- Tower Defense 경제 시스템 확장
- LoL과 차별화하기 위한 억지 기능 추가

## 22. 첫 구현의 최소 성공 기준

다음 6개가 성립하면 1차 전환은 성공으로 본다.

1. 플레이어가 Robot 1기를 직접 이동한다.
2. 플레이어가 직접 공격한다.
3. 플레이어가 타깃을 선택/전환한다.
4. 특수무기 1개를 직접 사용한다.
5. XP 획득과 즉시 레벨업이 유지된다.
6. 적 다수전이 기존 Tower Defense 조작 없이도 성립한다.

이 6개가 성립하기 전에는 AI 아군, 복잡한 지원 시설, 추가 무기, 대규모 UI 개편을 자동으로 진행하지 않는다.

## 23. 마리의 기술 판단

PROPOSAL:
기존 main.gd를 한 번에 전면 재작성하는 것보다, 현재 전투 루프를 유지하면서 Robot 직접조종 경로를 먼저 독립시키는 방식이 안전하다.

이유:
- 현재 맵/적/피해/XP/승패 시스템을 재사용할 수 있다.
- 한 번에 변경하는 변수가 줄어든다.
- 직접조종 전투의 재미를 가장 빨리 검증할 수 있다.
- 실패 시 기존 PoC와 차이를 추적하기 쉽다.

또한 Tower 시스템을 먼저 삭제하는 것은 권장하지 않는다. Canon은 Tower를 폐기하지 않고 지원 시설로 재정의했기 때문이다.

## 24. 마리의 판정 기준

현재 상태에서 "직접 조종 게임으로 완성되었다"고 판단하지 않는다.

판정은 다음 순서로 한다.
- Phase 1: 조작 가능 여부
- Phase 2: 공격/타깃 가능 여부
- Phase 3: 슈퍼로봇다운 무기 사용 여부
- Phase 4: HUD가 파일럿 중심인지
- Phase 5: 지원 시설이 보조 역할인지
- Phase 6: AI 아군이 조작을 방해하지 않는지
- Phase 7: 보스전이 동일 조작으로 성립하는지
- Phase 8: 캠페인 전체 루프가 성립하는지

각 단계가 성공하면 다음 단계로 자동 진행하지 않는다. Master 요청이 필요하다.

## 25. 최종 상태 정의

목표 최종 구조:

플레이어 Robot 직접조종
+ AI 아군
+ 고정형 지원 시설
vs
일반 적 다수
+ 거대 보스

기존 시스템의 기술적 자산은 가능한 한 재사용하지만, 기존 Tower Defense 중심 게임플레이를 보존하는 것을 목표로 하지 않는다.

즉, "기존 게임에 조작 기능을 붙이는 것"이 아니라 "기존 구현을 새 Canon에 맞게 역할 재배치하는 것"이 본 전환의 핵심이다.
