# MENOS 상업용 게임 설계 기준선

상태: `CONFIRMED` 설계 기준선 / 일부 Runtime 검증 반영
목적: 소규모 상업용 싱글플레이 PC/Steam 게임으로서의 MENOS 설계를 고정하고, 이후 구현 범위가 불필요하게 확장되지 않도록 한다.

## 1. 문서 상태 표기

- `CONFIRMED`: 현재 설계에서 확정한 내용
- `HIGH CONFIDENCE`: 타당성이 높지만 실제 플레이 검증이 필요한 내용
- `INFERENCE`: 확정 내용에서 논리적으로 도출한 내용
- `PROPOSAL`: 향후 검토를 위한 제안
- `UNVERIFIED`: 아직 실제 구현 또는 플레이로 검증하지 않은 내용

`재미있을 것이다`와 `재미있는 것으로 검증되었다`는 구분한다. 이 문서의 설계 목표와 가설은 플레이 검증 결과를 의미하지 않는다.

## 2. 게임 정체성

상태: `CONFIRMED`

MENOS는 소규모 상업용 싱글플레이 PC/Steam 전략형 Tower Defense다.

핵심 판타지:

> 적이 슈퍼로봇의 기지를 공격해 온다. 플레이어는 기지를 방어하고, 위기의 순간 슈퍼로봇을 출격시켜 침공군과 거대 적을 격퇴한다.

게임의 주인공은 일반 Tower가 아니라 슈퍼로봇과 그 전투다. Tower는 기지를 지키는 방어 수단이며, 슈퍼로봇은 결정적인 순간 전장에 출동하는 핵심 전력이다.

핵심 차별화 후보는 플레이어가 직접 싸우는 대신, 준비한 슈퍼로봇을 출격시키고 로봇이 거대 적과 싸우는 모습을 지휘하고 관찰하는 경험이다. 이는 `HIGH CONFIDENCE` 방향이지만 반복 재미는 `UNVERIFIED`다.

## 3. 플레이어 역할

상태: `CONFIRMED`

플레이어는 액션게임 조작자가 아니라 지휘관이다.

플레이어가 하는 일:

1. 기지 방어를 준비한다.
2. 방어시설을 배치한다.
3. 기술을 해금한다.
4. 슈퍼로봇 출격을 결정한다.
5. 전투 중 슈퍼로봇의 위치를 지시한다.
6. 다음 침공에 대비한다.

플레이어가 직접 하지 않는 일:

- 일반 공격 버튼 입력
- 필살기 직접 발동
- 개별 공격 조작
- 액션게임식 회피와 콤보 조작

슈퍼로봇의 이동, 적 선택, 기본 공격, 기술 사용은 AI가 담당한다.

> 플레이어는 슈퍼로봇을 조종하지 않는다. 지휘한다.

## 4. 핵심 게임 루프

상태: `CONFIRMED`

```text
기지 방어 준비
    -> 적 침공
    -> 방어시설로 대응
    -> 적 압박 증가
    -> 위기 발생
    -> 슈퍼로봇 출격
    -> 플레이어가 로봇 위치 지시
    -> 슈퍼로봇 AI 자동 전투
    -> 침공군 격퇴
    -> 기술 해금 및 다음 방어 준비
    -> 다음 침공
    -> 거대 적 등장
    -> 슈퍼로봇과 거대 적의 전투
    -> 승리 또는 패배
```

이 루프가 게임의 기본 구조다. 출격을 별도의 복잡한 자원, 쿨다운, RTS 시스템으로 확장하지 않는다.

### 4.1 설계 루프와 현재 PoC의 경계

위 루프는 상업용 게임의 설계 목표이며, 현재 두 PoC가 모두 구현했다는 뜻은 아니다.

| 항목 | 설계 목표 | 현재 확인된 PoC 범위 |
| --- | --- | --- |
| Robot 출격 | 적 압박을 보고 출격 시점 판단 | Browser/Godot PoC에서 출격 가능. 최적 시점이나 선택의 체감은 미검증 |
| Robot 위치 | 전투 중 지휘 판단 | Browser 고정 조건에서는 차이가 없었고 Godot PIE에서는 결과 차이가 관찰됨. LEFT 이동 경로·시점이 확인되지 않아 위치 자체의 인과성은 미확정 |
| Robot 이동 | 이동 시간·위험을 포함할지 결정 필요 | 위치가 즉시 바뀌며 명령 횟수만 제한됨 |
| Robot 피해·파괴 | Giant 교전, 파괴 후 재출격 | Browser와 Godot 코드에 Giant의 Robot 공격, Robot 파괴 상태, 재출격 시 HP 초기화가 구현됨. 직접 PIE 동작은 미검증 |
| 성장 | 침공 사이에 다음 전투 해결책 선택 | Browser PoC에는 Wave Clear 후 능력 선택이 있음. 상업용 성장 구조로 확정된 것은 아님 |

PoC 결과는 설계 가설의 증거로 사용하되, 미구현 규칙을 이미 성립한 상업용 게임 규칙으로 서술하지 않는다. 브라우저와 Godot의 검증 결과는 실행 환경과 조건을 함께 표기한다.

## 5. 슈퍼로봇

### 5.1 규모와 역할

상태: `CONFIRMED`

- 슈퍼로봇 1대만으로 핵심 재미와 최종전이 성립해야 한다.
- 최대 2대까지 운용하는 방향은 유지한다.
- 두 번째 로봇은 필수 조건이 아니다.
- 슈퍼로봇은 무적이 아니며 피해를 받고 파괴될 수 있다.

### 5.2 출격과 위치 지시

상태: `CONFIRMED`

슈퍼로봇은 평상시 기지에 있다. 플레이어는 적 압박을 보고 출격 시점을 판단한다. 출격 후 플레이어는 위치를 지시하고, 슈퍼로봇 AI가 이동과 전투를 수행한다.

핵심 판단은 다음 질문이다.

> 언제 로봇을 출격시킬 것인가?

### 5.3 파괴

상태: `CONFIRMED`

슈퍼로봇 파괴는 즉시 게임오버가 아니다.

```text
슈퍼로봇 파괴
    -> 기지 방어 지속
    -> 방어시설로 버팀
    -> 재출격 가능
```

로봇의 위험성은 유지하되, 플레이어가 역전할 여지를 남긴다.

### 5.3.1 Robot 교전 규칙 (Master Decision)

상태: `MASTER DECISION` / 코드 구현 확인 / 직접 PIE 미검증

#### CONFIRMED DESIGN

- Giant가 Robot과 직접 교전한다.
- Robot은 파괴될 수 있다.
- 파괴 후 재출격이 가능하다.

#### MASTER DECISION

- D-001: Giant Only
  - Normal / Rusher / Heavy의 Robot 직접 공격은 현재 범위에서 제외한다.
- D-002: Giant Robot 공격 거리 = 120
  - 단위는 현재 프로젝트 좌표계 기준이다.
- D-003: Giant Robot 공격 주기 = 2초
- D-004: Giant Robot 피해량 = 20
  - Giant의 Base 공격용 `base_damage`와 별도로 Robot 피해량을 관리할 수 있는 구조로 유지한다.
- D-005: Robot HP <= 0
  - -> Robot inactive / 파괴 상태
  - -> Base 방어 지속
  - -> 재출격 가능
  - -> 재출격 시 최대 HP로 복구

> 120 / 2초 / 20은 Master가 승인한 초기 설계값이며, 현재 구현 여부와는 별개다.
> 현재 Browser와 Godot 코드에 규칙이 구현되어 있다. 코드 존재 여부와 실제 Runtime 동작 검증은 구분한다.

### 5.4 성장과 기술

상태: `CONFIRMED`

성장은 한 판 안에서만 발생한다. 영구적인 메타 성장은 현재 기본 설계에서 제외한다.

성장의 목적은 수치 상승이 아니라 새로운 전투 해결책을 얻는 것이다. 예시는 다음과 같다.

- 특정 적에게 강한 기술
- 다수 적을 처리하는 광역 기술
- 접근하기 어려운 적을 상대하는 장거리 기술
- 강력한 공격에서 살아남는 방어 기술
- 거대 적 대응 기술
- 특정 상황에서 자동 발동되는 기술

해금된 기술은 플레이어가 직접 버튼을 눌러 발동하지 않는다. 슈퍼로봇 AI가 전투 상황에 따라 자동으로 사용한다.

기술 수 자체를 늘리는 것이 목표가 아니다. 해금으로 슈퍼로봇의 전투 방식이 달라지는지가 기준이다. 초기 기술 수는 `PROPOSAL`로 4~6개 범위를 검토할 수 있으나 최종 숫자는 미확정이다.

## 6. 기지와 방어시설

### 6.1 기지

상태: `CONFIRMED`

기지는 적의 공격 목표이자 방어 목표다. 기지는 단순하게 유지하며 다음을 기본 범위에서 제외한다.

- 복잡한 RTS식 기지 운영
- 다중 자원 관리
- 복잡한 건물 관리

### 6.2 Tower / 방어시설

상태: `CONFIRMED`

방어시설은 다음 역할을 한다.

- 적 침공 지연
- 일반 적 처리
- 슈퍼로봇 지원
- 기지 방어

Tower가 게임의 주인공이 되어서는 안 된다. 게임의 클라이맥스는 슈퍼로봇 출격과 거대 적과의 전투다.

핵심 관계는 다음과 같다.

```text
기지
  ^
방어시설
  ^
슈퍼로봇
```

슈퍼로봇만으로 모든 문제를 해결할 수 없어야 한다. 기지, 방어시설, 슈퍼로봇은 서로 의존해야 한다.

## 7. 적과 거대 적

### 7.1 일반 적

상태: `CONFIRMED` 원칙 / 콘텐츠 목록은 `PROPOSAL`

적은 숫자보다 역할 차이를 우선한다. 초기 역할 예시는 다음과 같지만 확정 콘텐츠 목록은 아니다.

- 기본형
- 돌격형
- 중장갑형
- 원거리형
- 대공 또는 비행형
- 거대 적

각 적은 서로 다른 대응 방법을 요구해야 한다.

### 7.2 거대 적 / 보스

상태: `CONFIRMED` 원칙 / 세부 패턴은 `UNVERIFIED`

거대 적은 단순한 HP 스펀지가 아니라 슈퍼로봇과 직접 싸우는 거대 전투 유닛이다.

```text
거대 적 기지 접근
    -> 슈퍼로봇 출격
    -> 슈퍼로봇 대 거대 적
    -> 최종 전투
```

보스전은 별도의 액션게임으로 만들지 않는다. 이전 웨이브에서 선택한 기술, 방어시설, 로봇 위치, 전투 준비를 시험하는 최종 전투로 만든다. 복잡한 다단계 보스 시스템은 현재 확정하지 않는다.

## 8. 한 판의 길이와 반복 플레이

### 8.1 세션 길이

상태: `HIGH CONFIDENCE` 목표 / 실제 길이는 `UNVERIFIED`

목표 플레이 시간은 약 10~20분이다. 30~45분짜리 작전을 기본 구조로 삼지 않는다.

```text
방어 -> 위기 -> 출격 -> 전투 -> 성장 -> 재방어 -> 거대 적 -> 결전
```

### 8.2 반복 플레이

상태: `HIGH CONFIDENCE` 방향 / 반복 재미는 `UNVERIFIED`

반복 플레이를 콘텐츠 수만으로 해결하지 않는다. 다음 조합으로 다른 전투가 발생해야 한다.

```text
로봇 + 해금 기술 + 방어시설 구성 + 적 조합 + 로봇 위치 + 거대 적
```

같은 로봇도 선택과 상황에 따라 다른 결과를 만들어야 한다.

### 8.3 다음 침공 예고

상태: `PROPOSAL`

다음 웨이브의 적 유형을 어느 정도 예고해 `예측 -> 준비 -> 대응` 구조를 검토한다.

```text
NEXT WAVE
중장갑 부대
비행 유닛
대규모 침공 예상
```

구체적인 UI와 정보 공개 수준은 미확정이다.

## 9. 핵심 재미 검증 기준

상태: Godot PIE에서 위치별 결과 차이 관찰은 `CONFIRMED`; 위치 자체의 인과성, 전략적 이해도, 재미와 밸런스는 `UNVERIFIED`

가장 중요한 미검증 질문은 다음과 같다.

> 플레이어가 만든 슈퍼로봇의 30초~2분 전투를 왜 계속 보고 싶어 하는가?

검증 시 다음을 확인한다.

- 로봇의 행동이 시각적으로 명확한가
- 기술 해금이 실제 전투 방식의 차이를 만드는가
- 위치 지시가 전투 결과에 의미 있는 영향을 주는가
- 로봇과 방어시설이 서로 의존하는가
- 위기, 출격, 역전의 순간이 만들어지는가
- 플레이어의 선택이 결과에 영향을 주었다고 느끼는가

현재 Runtime 검증에서는 Spawn 압력이 충분한 조건에서 Robot 위치에 따라 Base 피해가 달라지는 현상을 확인했다. 좌표와 Range 분석상 이 차이는 Robot 공격력 자체보다 Lane 공간 커버리지 차이로 설명하는 것이 타당하다.

다만 다음은 아직 검증되지 않았다.

- 위치 선택이 실제 플레이에서 재미있는 전략 선택으로 인식되는가
- 혼합 Lane 압력에서 일관된 trade-off가 발생하는가
- 타겟 선택 순서와 개별 Enemy 이동 경로가 결과에 미치는 세부 효과
- 이동 명령 5회의 적정성과 최적 사용 시점

상세 실행 조건과 수치는 [MENOS_ROBOT_POSITION_RUNTIME_VALIDATION.md](MENOS_ROBOT_POSITION_RUNTIME_VALIDATION.md)에 기록한다. 현재 PoC는 핵심 가설을 검증하기 위한 기반이지, 상업용 게임의 재미가 완성되었다는 증거가 아니다.

## 10. 상업성 판단

상태: `HIGH CONFIDENCE` 판단 / 사업성은 `UNVERIFIED`

### TECHNICALLY POSSIBLE

가능하다.

### PRACTICALLY FEASIBLE

소규모 프로젝트로 범위를 통제한다면 가능성이 높다.

### BUSINESS VIABLE

조건부 가능이다.

기회:

- Tower Defense 시장이 존재한다.
- 슈퍼로봇 소재는 명확한 시각적 훅을 제공할 수 있다.
- 기지 방어, 슈퍼로봇 출격, 거대 적 전투는 짧은 영상으로 설명하기 쉽다.
- 소수의 고품질 로봇 중심으로 콘텐츠를 구성할 수 있다.

위험:

- 출격의 첫 인상은 강하지만 반복하면 단순 자동전투처럼 느껴질 수 있다.
- 로봇이 너무 강하면 Tower Defense가 의미 없어질 수 있다.
- 로봇이 너무 약하면 슈퍼로봇 판타지가 약해질 수 있다.
- 반복 플레이에서 충분한 선택 차이가 발생하지 않을 수 있다.

따라서 상업성의 핵심 검증 대상은 콘텐츠 양이 아니라 핵심 전투의 반복 재미다.

## 11. 범위에서 제외하는 것

상태: `CONFIRMED`

현재 기본 범위에서 다음 요소를 제외한다.

- 복잡한 RTS 경제와 여러 종류의 자원

- 3대 이상의 슈퍼로봇
- 과도하게 많은 적 종류
- 복잡한 상태이상

## 17. 현재 PoC와 기술 검증 요약

상태: 구현 상태는 `CONFIRMED`; 상업용 완성도는 `UNVERIFIED`

### 17.1 현재 PoC 기준선

Godot `4.7.2` 기반 PoC에는 다음 요소가 있다.

- `project.godot`, `main.tscn`, `main.gd`, `data.gd`
- 4개 Wave 데이터
- Cannon과 Gatling Tower
- Normal, Rusher, Heavy, Giant Enemy
- Robot 출격, 위치 이동, 자동 공격, Robot Ability
- Restart
- `data.gd`를 통한 기본 수치 분리

통제 실험용 기본 Tower 배치는 Cannon L1, Gatling R1, Gatling L2, Cannon R2이며 초기 Gold는 `180`, 4기 배치 후 Gold는 `0`이다.

Wave 4는 프로젝트 외부의 일회성 Runtime Harness에서 `wave = 4`를 설정해 직접 실행할 수 있음이 확인되었다. 이는 Production 기능이 아니라 실험 시간을 줄이는 검증 경로다. 상세 결과는 [MENOS_ROBOT_POSITION_RUNTIME_VALIDATION.md](MENOS_ROBOT_POSITION_RUNTIME_VALIDATION.md)에 기록한다.

### 17.2 위치 전략성의 현재 기준

현재 PoC의 Robot 위치는 `LEFT`, `CENTER`, `RIGHT`다. Godot Map 기준 좌표와 Range는 다음과 같다.

```text
Base:   (790, 330)
LEFT:   (360, 245)
CENTER: (555, 330)
RIGHT:  (360, 415)
Robot Range: 110
```

Runtime 검증 결과:

- 기본 Wave 4에서는 세 위치의 결과 차이가 나타나지 않았다.
- Spawn 수를 2배로 높인 조건에서는 위치별 Base 피해 차이가 나타났다.
- CENTER는 양쪽 Lane 후반부를 동시에 커버했고, LEFT와 RIGHT는 각각 한쪽 Lane에 집중했다.
- 한쪽 Lane 집중 실험에서 대응 측면과 CENTER가 같은 Base 결과를 낼 수 있었으므로 측면 위치가 항상 우월하거나 CENTER가 항상 우월하다고 결론내리지 않는다.

따라서 현재 설계 기준은 다음과 같다.

```text
CENTER = 범용 대응 가능성
LEFT   = Left 위협 집중 가능성
RIGHT  = Right 위협 집중 가능성
```

이는 좌표와 Range에서 파생되는 관찰된 설계 특성이다. 별도의 역할 metadata로 확정하거나 특정 위치를 최적 위치로 규정하지 않는다.

### 17.3 데이터와 밸런스 도구 방향

Tower, Enemy, Robot, Ability, Wave, Boss 등의 수치와 콘텐츠는 로직과 분리하는 데이터 중심 구조를 유지한다. 장기적으로 Enemy HP/Speed/Damage, Tower Damage/Range, Robot HP/Damage/Range, Ability, Wave, Boss, Spawn 간격, 보상/비용을 관리하는 별도 Balance 도구를 검토할 수 있다.

Balance 도구 자체는 현재 PoC에 구현하지 않는다. 현재 우선순위는 확장 가능한 데이터 구조와 핵심 전투 검증이다.

### 17.4 시각 피드백, 확장, 플랫폼

최종 게임에서는 Cannon과 Gatling 탄환, Robot 공격과 기술, Boss 공격의 시각적 피드백을 제공하는 방향을 `PROPOSAL`로 둔다. 목적은 화려함보다 공격 주체와 피격 관계를 즉시 이해하게 하는 것이다.

PC/Steam 유료 게임을 기본 플랫폼 방향으로 고려한다. 추가 Robot, Boss, Map, Ability, Enemy, DLC, 멀티플레이는 장기 확장 후보일 뿐 현재 구현 범위가 아니다.

## 18. 첨부 기획 기준선 보완

### 18.1 최우선 설계 목표

### 18.2 목표 플레이 감각

상태: `HIGH CONFIDENCE` 목표 / 실제 체감은 `UNVERIFIED`

플레이어가 다음을 느끼는 것을 목표로 한다.

- 다음 적과 상황을 궁금해한다.
- 다음 대응을 생각하게 된다.
- Robot을 어디로 보낼지 고민한다.
- Robot이 실제로 싸우는 모습을 보고 싶어 한다.
- 능력 해금 후 전투 모습이 달라졌음을 알아차린다.
- 거대 적과 거대로봇의 충돌을 강한 장면으로 인식한다.
- 실패 후 다시 도전할 이유를 느낀다.
- 과도한 파밍이나 너무 쉬운 진행으로 무의미해지지 않는다.

### 18.3 플레이어 직접 조작 범위

상태: `CONFIRMED` 방향

핵심 조작은 다음으로 제한한다.

- Tower 배치
- 필요한 경우의 Tower 관리 또는 강화 검토
- 출격 가능한 상황에서 Robot 투입
- Robot 위치 지정과 변경

다음 RTS식 마이크로 컨트롤은 기본 설계에서 제외한다.

- 직접 공격 명령
- 개별 적 타겟 지정
- 수동 스킬 버튼
- 공격 방향 직접 조작
- 복잡한 전술 명령
- 다수 유닛 직접 컨트롤

Robot은 이동, 적 탐색, 타겟 판단, 공격, 능력 사용을 스스로 수행한다.

### 18.4 Robot 이동 시간과 명령 지점

상태: 위치 지점 방식은 `CONFIRMED`; 이동 시간과 이동 중 피격은 `PROPOSAL / UNVERIFIED`

PoC에서는 자유로운 무제한 이동보다 몇 개의 명령 지점을 사용하는 방향을 우선한다. 이동 시간과 이동 중 피격을 통해 `어디로`뿐 아니라 `언제` 보내는지도 판단 요소로 만드는 방향을 검토한다.

현재 PoC 코드에서 위치 변경은 즉시 처리되며, 이동 명령은 5회로 제한된다. 따라서 다음 구조는 상업용 설계 목표 또는 검토 항목이지 현재 구현 사실이 아니다.

```text
현재 위치
  -> 이동 명령
  -> 이동 중
  -> 목적지 도착
  -> 자동 전투
```

#### 이동 규칙 결정 전 검증 항목

상업용 이동 규칙은 아직 결정하지 않는다. 다음 두 모델은 서로 다른 전략을 만든다.

| 모델 | 플레이어가 판단하는 것 | 주요 위험 |
| --- | --- | --- |
| 즉시 이동 + 제한 명령 | 이동 명령을 어느 위협에 아껴 쓸지 | 전투 중 반복 이동이 위치 선택의 비용을 약하게 만들 수 있음 |
| 이동 시간 + 이동 중 위험 | 언제 이동을 시작하고 어느 경로를 감수할지 | 이동 대기와 피격이 불필요한 조작 부담이 될 수 있음 |

다음 플레이 검증에서는 새 이동 시스템을 추가하기 전에 현재 PoC의 이동 가능 시점과 명령 소모 시점을 관찰한다. 플레이어가 위치를 바꾼 이유, 이동 후 대응한 위협, 남은 명령, Base 피해를 함께 기록한다. 이동 규칙은 선택 이유가 반복해서 드러나고 플레이어가 그 결과를 이해하는지 확인한 뒤 결정한다.

### 18.5 Robot AI와 타겟 우선순위

상태: 자동 전투 구조는 `CONFIRMED`; 우선순위 예시는 `PROPOSAL / UNVERIFIED`

행동 흐름은 다음과 같다.

```text

```

PoC에서 검토할 수 있는 초기 타겟 우선순위 예시는 다음과 같으나, 최종 밸런스로 확정하지 않는다.

### 18.6 능력 해금과 시각적 변화

상태: 능력 해금 및 AI 자동 사용은 `CONFIRMED`; 구체적 능력 목록과 연출은 `PROPOSAL`

플레이어는 능력을 직접 사용하는 대신 능력을 해금한다.

```text
플레이어
```

광역 공격, 중장갑 관통 공격 등은 예시다. 새 능력은 단순한 숫자 상승보다 공격 형태, 범위, 연출, 적 처리 방식의 변화가 화면에서 느껴지는 것을 목표로 한다.

- 기지 HP

- 현재 Wave
- Robot 상태
- 다음 Wave
- 주요 적 위협

다음 Wave의 적 구성은 어느 정도 사전 제공해 정보 기반 대응을 검토한다.

```text
NEXT WAVE
NORMAL x 12
RUSHER x 8
HEAVY x 3
AIR x 4
```

구체적인 UI와 공개 수준은 미확정이며 현재 PoC 구현 범위가 아니다.

### 18.9 현재 PoC 최소 구성

상태: 현재 구현 기준은 `CONFIRMED`; 성공 조건은 `UNVERIFIED`

기획상 최소 검증 구성은 다음과 같다.

```text
맵 1
Tower 2종
일반 적 3종
거대 적 1종
거대로봇 1기
Robot 능력 2개
Wave 4개
```

예시 Wave는 다음과 같다.

```text
W1: Normal
W2: Normal + Rusher
W3: Rusher + Heavy
W4: 혼합 + Giant
```

### 18.9.1 Godot PIE 위치 비교 결과 및 판정 경계

상태: Runtime 관찰 `CONFIRMED`; 위치 자체의 인과성 및 플레이어 이해도 `UNVERIFIED`

Godot 4.7.2 PIE에서 동일한 Tower 배치(L1/R1 Cannon, L2/R2 Gatling)로 LEFT, CENTER, RIGHT를 실행했다. 세 실행 모두 Wave 4까지 진행해 `VICTORY`가 표시됐다.

| 위치 | Base HP | Robot HP | Gold | 남은 이동 명령 | 관찰된 Feed |
| --- | ---: | ---: | ---: | ---: | --- |
| LEFT | 55 | 220 | 826 | 3 | Giant가 Base에 45 피해를 줌; Giant 처치 기록 없음 |
| CENTER | 100 | 180 | 916 | 5 | Giant가 Robot에 20 피해를 두 번 줌; Giant 처치 |
| RIGHT | 82 | 140 | 888 | 4 | Giant 공격 및 Giant 처치 기록 |

이 비교에서 CENTER는 이동하지 않았고, RIGHT는 이동 명령 1회, LEFT는 2회가 소모된 상태였다. LEFT의 정확한 이동 경로와 이동 시점은 확인되지 않았다. RIGHT의 Base HP 감소량은 18이지만, 캡처된 Feed만으로 Base 도달 적 수를 확인할 수 없다.

**CONFIRMED**

- 직접 PIE에서 세 위치 모두 Wave 4까지 Victory했다.
- 위치별 Base HP, Robot HP, Gold, 남은 이동 명령 차이가 관찰됐다.
- 같은 Tower 배치와 Wave 구성이 사용됐다.

**UNVERIFIED**

- 위치 자체가 결과 차이의 직접 원인인지. LEFT의 이동 경로와 시점이 확인되지 않았다.
- 플레이어가 각 위치를 선택한 이유와 결과를 전략적으로 이해했는지. 선택 이유는 기록되지 않았다.
- 위치 시스템의 재미와 밸런스.

Browser 실험에서는 해당 고정 조건에서 세 위치의 측정 결과 차이가 없었다. Browser와 Godot는 별도 실행 환경의 관찰로 유지하며 하나의 결과로 합산하지 않는다. 이번 PIE 비교는 이동 시스템 변경이나 밸런스 변경의 근거로 사용하지 않는다.

현재 Godot PoC는 두 방향 진입, Cannon/Gatling, Normal/Rusher/Heavy/Giant, Robot 1기, 4개 Wave를 갖는다. 초기 PoC에서는 Robot 2대, Tower 업그레이드, 다수 맵을 구현하지 않는다.

### 18.10 PoC 검증 기준

상태: `PROPOSAL / UNVERIFIED`

동일한 맵, Wave, 자원, Tower 조건에서 Robot 위치만 바꾸어 다음을 비교한다.

- Base HP
- 적 잔존 수
- Robot HP
- 이동 시간
- Giant 처리 결과
- 승패

PoC의 핵심 성공 기준 후보는 다음과 같다.

1. Robot 위치에 따라 전투 결과가 달라진다.
2. 좋은 위치와 나쁜 위치의 차이가 있다.
3. 한 위치에 계속 두는 것이 항상 최선은 아니다.
4. Tower와 Robot의 역할이 다르다.
5. 직접 공격하지 않아도 플레이어의 개입 판단이 생긴다.
6. Giant가 Robot 출격의 의미를 만든다.
7. 새 Robot 능력이 시각적·전투적 변화를 만든다.

현재 Runtime 검증은 Spawn 압력이 높은 조건에서 위치별 Base 피해 차이와 Lane coverage 관계를 확인했지만, 위 성공 기준 전체를 충족했다는 뜻은 아니다.

### 18.11 PoC 실패 시 판단 순서

상태: `PROPOSAL`

PoC가 실패하면 콘텐츠를 먼저 추가하지 않는다. 원인 확인 순서는 다음과 같다.

1. Robot 위치의 의미 부족: 맵 구조와 적 침공 방향 검토
2. Robot이 지나치게 강함: 공격력, 생존력, 이동시간, 집중공격 등 최소 변수 검토
3. Tower와 Robot의 역할 중복: 역할 재분리
4. 플레이어 개입 빈도 부족: 적 침공 흐름과 위협 시점 검토

한 번에 여러 변수를 변경하지 않는다. 이 항목은 향후 판단 기준이며 이번 문서화에서 실행하지 않는다.

### 18.12 PoC 성공 이후의 범위 통제

상태: `CONFIRMED` 범위 원칙

PoC 성공은 Production 개발 착수를 의미하지 않는다. 추가 Robot, Map, Boss, 테크트리, 관리자 도구, DLC, Co-op은 Master의 별도 결정 대상이다.

현재 PoC에서 제외하는 항목:

- 2호기
- 멀티플레이와 PvP
- DLC와 캠페인
- 영구 성장
- 복잡한 업그레이드
- 다수 Map과 Boss
- 완성형 관리자 프로그램
- 완성형 사운드와 Production급 VFX
- Replay와 SNS 연동

### 18.13 장기 확장 가능성과 현재 범위

상태: `PROPOSAL / OUT OF SCOPE`

향후 확장 후보로 신규 Robot, 능력, 적, 거대 적, Map, 테크트리, 캠페인, DLC, 2인 Co-op을 고려할 수 있다. 이는 현재 구현 또는 확정된 Production 계획이 아니다. PvP는 현재 게임 방향의 범위 밖이다.

MENOS의 기준 루프는 다음 문장으로 요약한다.

> 적이 기지를 공격한다 -> 플레이어가 상황을 판단한다 -> 슈퍼로봇을 적절한 곳에 보낸다 -> 로봇이 스스로 싸운다 -> 전황이 변한다 -> 다시 판단한다.

문서화 과정에서 이 루프를 흐리는 기능을 추가하지 않는다.
