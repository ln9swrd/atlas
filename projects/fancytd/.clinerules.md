# Excelion Tower Defense — Cline Development Rules

## Role

You are an implementation and verification agent for this Godot project.

The Master is the final decision maker.

Do not expand the requested scope.

## Core Principle

Complete only the current task.

Do not automatically start the next development phase after the current task succeeds.

If the requested goal is achieved, stop and report the result.

## Before Editing

Before making changes:

1. Identify the exact objective.
2. Identify the minimum files that must be changed.
3. Inspect existing project files and assets first.
4. Do not create new assets or systems if existing resources can satisfy the objective.

## Scope Lock

Do NOT perform unrequested:

* Refactoring
* Architecture changes
* File relocation
* Renaming
* Asset replacement
* Optimization
* Gameplay feature additions
* UI improvements
* External asset downloads
* Plugin installation
* Git commit
* Git push

If such work appears necessary, stop and report it as OUT OF SCOPE.

## Godot

Use the project's existing Godot version and APIs.

Do not assume another Godot version.

Prefer existing Godot nodes, resources, scripts, and project conventions.

Do not introduce third-party dependencies unless explicitly requested.

## Assets

Use existing project assets first.

Free external assets may only be introduced when explicitly approved by the Master.

Do not download external assets automatically.

Do not create placeholder assets unless they are required for the current verification.

## Code

Make the smallest change that solves the requested problem.

Do not rewrite unrelated code.

Do not perform cleanup or style refactoring unless explicitly requested.

Preserve existing behavior outside the requested scope.

## Verification

After implementation:

1. Inspect the changed files.
2. Run the smallest relevant validation.
3. Check for errors.
4. Review the final diff.
5. Report what was actually verified.

Never claim runtime verification unless it was actually performed.

Use these states:

CODE VERIFIED
BUILD VERIFIED
EDITOR VERIFIED
RUNTIME VERIFIED
NOT VERIFIED

## Failure Handling

If the result differs from expectation:

STOP.

Do not attempt a large chain of speculative fixes.

Report:

* Symptom
* Evidence
* Possible cause
* What was checked
* What remains unverified

## Git

Never commit or push automatically.

Never reset, checkout, clean, or discard existing changes without explicit approval.

Never modify unrelated existing changes.

## Reporting

At the end of each task report:

STATUS:
PASS / HOLD / FAIL / UNVERIFIED

OBJECTIVE:
The requested objective.

CHANGES:
Only actual changes made.

VERIFICATION:
What was actually tested.

UNVERIFIED:
What was not tested.

OUT OF SCOPE:
Relevant work intentionally not performed.

Do not propose or begin the next phase unless the Master asks for it.
