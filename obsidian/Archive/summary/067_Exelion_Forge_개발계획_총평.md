# Exelion Forge 개발계획 총평 · Project Charter

## 총평 요약
| 항목 | 점수 |
|------|------|
| 세계관/비주얼 | 9/10 |
| 게임성 | 8/10 |
| 차별성 | 8.5/10 |
| 개발 현실성 | 5/10 |
| 수익화 | 7/10 |
| **전체** | **7.5/10** |

컨셉은 강하나, **완성 가능한 범위로 축소** 필요.

## 핵심 문제
장르 4개 혼합 (디펜스 + 슈팅 + RTS + RPG) → 1인 개발에 과다.

## MVP 권장
**디펜스 + 메가캐논 + 오버히트**만 남김.
제거: 월드맵, 보급선, 점령, 연구소, 군수공장.
남김: Excelion, Noiko, Overheat, Boss.

## 핵심 의사결정 루프
> "지금 과열을 감수하고 쏠까?"

오버히트가 게임의 중심. 메가캐논보다 오버히트 관리가 핵심 재미.

## 개발 단계
1. **프로토타입**: Excelion 1기, Noiko 2기, Overheat, 적 5종, 보스 1종
2. **얼리액세스**: 파츠 개조, 드론 스킬트리, 스테이지 10개
3. **정식**: 월드맵, 보급선, 점령전, 캠페인

## 플랫폼
초기 **PC(Steam) 전용** 권장. 모바일은 UI·터치·성능으로 작업량 2배.

## 진짜 경쟁력
메카 디자인이 아니라 **"1인 개발자가 AAA급 개발 체계를 갖춘 프로젝트"**.
Vision · Design Bible · Coding Standard · Asset Pipeline · Sprint 등.

## 재사용 원칙
Excelion에서 만든 시스템(이동, 카메라, 락온, AI, 보스, 미션, 저장)은 다음 작품에서도 쓸 수 있도록 컴포넌트화.

## PROJECT CHARTER (핵심 원칙)
1. **완성이 가장 중요하다** — 미완성의 훌륭한 게임보다 완성된 좋은 게임
2. 플레이어 시간 존중 — 반복은 있어도 지루함은 없어야
3. 단순함 선택 — 복잡함은 마지막 선택
4. 매 Sprint마다 플레이 가능 결과물
5. 기술보다 경험 (그래픽·연출보다 플레이 감각)
6. 지속 가능한 개발 — 6개월 후에도 유지보수 가능
7. 자동화 — 반복 작업은 도구로, 개발자는 창조에 집중

기능 추가 시 질문:
- 더 재미있어지는가?
- 출시를 더 가깝게 만드는가?
둘 다 아니면 추가하지 않는다.

## 진행 방식
문서 중심 → **Sprint 중심** 전환.
Sprint마다: 목표 / 하지 않을 것 / 최소 완성 기능 / 플레이 검증 항목.
