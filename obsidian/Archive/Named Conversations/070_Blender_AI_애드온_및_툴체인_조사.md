블렌더 파일을 깃에 저장하는 건 어떨까?

나는 **적극 추천**하는 편이야. 다만 `.blend` 파일은 소스코드처럼 다루면 안 되고, 운영 방식을 조금 달리해야 해.

## 장점

### 1. 작업 이력 관리

모델을 크게 수정했다가 마음에 안 들면 이전 버전으로 돌아갈 수 있다.

예를 들어

```
v0.1 : 기본 비율
v0.2 : 팔 구조 변경
v0.3 : 리토폴로지
v0.4 : UV 완료
```

처럼 언제든 복구 가능하다.

---

### 2. 프로젝트와 코드가 같이 관리된다

예를 들면

```
excelion-forge/
├── docs/
├── scripts/
├── addons/
├── assets/
│   ├── mecha.blend
│   ├── pilot.blend
│   └── effects.blend
└── README.md
```

AI가 작업할 때도 같은 저장소에서

- Python 스크립트
- Blender 애드온
- 모델
- 문서

를 모두 참조할 수 있다.

---

### 3. 백업

GitHub는 사실상 오프사이트 백업 역할도 한다.

SSD가 고장나도 복구가 가능하다.

---

## 단점

### Git은 .blend의 내용을 비교(diff)하지 못한다.

코드라면

```
+ this line
- that line
```

처럼 비교되지만,

`.blend`는 바이너리 파일이라

```
model.blend
```

전체가 하나의 덩어리로 저장된다.

누가 무엇을 수정했는지 비교는 거의 불가능하다.

---

### 용량이 금방 커진다

블렌더 파일은

```
20MB
50MB
150MB
500MB
```

가 흔하다.

Git은 변경될 때마다 내부적으로 버전을 관리하기 때문에 저장소가 빠르게 커질 수 있다.

---

## 그래서 업계에서는?

대부분 다음과 같이 한다.

```
Git
 ├─ 코드
 ├─ 애드온
 ├─ 문서
 ├─ 작은 blend
 └─ 설정

Git LFS
 ├─ 큰 blend
 ├─ FBX
 ├─ Texture
 ├─ HDRI
 └─ EXR
```

즉,

- 코드 → Git
- 대용량 에셋 → Git LFS

로 분리하는 경우가 많다.

---

## 혼자 개발이라면

혼자라면 더 단순하게 운영해도 된다.

- 100MB 이하의 `.blend`는 그냥 Git에 커밋
- 100~200MB 이상이 많아지면 Git LFS 도입 고려
- 큰 텍스처, 렌더 결과물은 저장소에 넣지 않고 별도 관리

---

## Atlas + Exelion에서는

현재 네 프로젝트 구조를 생각하면 오히려 Git 활용도가 높다.

```
Atlas
    docs
    python
    blender addon
    automation

Exelion Forge
    character.blend
    weapon.blend
    enemy.blend
    scripts
    docs
```

이렇게 하면 AI가 문서와 스크립트를 참고하면서 같은 저장소의 블렌더 에셋을 함께 관리할 수 있다.

### 내가 추천하는 운영 방식

- **`.blend` 원본은 Git으로 버전 관리한다.**
- **자동 저장(`.blend1`, `.blend2`) 파일은 `.gitignore`에 추가한다.**
- **렌더 이미지, 캐시, 시뮬레이션 결과물은 커밋하지 않는다.**
- 프로젝트가 커져 `.blend` 파일이 수백 MB 수준으로 늘어나면 **Git LFS**로 전환한다.

이 방식이면 지금처럼 **1인 개발 + AI 협업** 환경에서 관리 부담이 적고, 작업 이력과 복구 능력도 충분히 확보할 수 있다.

찾아보니 **네가 구상하는 방향과 상당히 비슷한 프로젝트들이 이미 조금씩 나타나기 시작했어.** 다만 **'전부를 하는 프로젝트'는 아직 없고**, 각각 일부 기능만 구현하고 있다.

내가 가장 주목한 것들을 정리해볼게.

---

# 1. BlenderForge ⭐⭐⭐⭐⭐ (가장 비슷)

**가장 네 방향과 가까운 프로젝트.**

- AI ↔ Blender 연결(MCP)
- 자연어로 모델 생성
- Python 스크립트 생성
- PolyHaven, Sketchfab 연동
- 40개 이상의 Blender 기능을 AI가 호출 가능

이 프로젝트는

> "AI에게 Blender를 조작시키자"

라는 철학이다.

하지만 **Exelion Forge**처럼

- 게임용 캐릭터 생성
- 메카 생성
- 프로젝트 전용 파이프라인

까지는 제공하지 않는다.

---

# 2. BlenderGPT ⭐⭐⭐⭐☆

이건 AI가 Blender Python을 생성한다.

예를 들면

> 숲을 만들어줘

↓

Python 생성

↓

Blender에서 실행

↓

장면 생성

애니메이션 생성도 일부 지원한다.

---

# 3. MB-Lab ⭐⭐⭐⭐⭐

이건 유명하다.

무료 캐릭터 생성기.

- 사람 생성
- 얼굴
- 체형
- 의상
- 파라미터 변경

등을 지원한다.

---

# 4. HumGen3D

상용이지만 코드 일부는 공개되어 있다.

엄청난 수준의

- 캐릭터 생성
- 얼굴
- 의상

을 제공한다.

---

# 5. Blender Skills ⭐⭐⭐⭐⭐

이건 굉장히 흥미롭다.

AI에게

> Blender 작업 지식

을 학습시켜 주는 프로젝트다.

즉

- 모델링
- 게임 에셋 제작
- 재질
- Blender Workflow

같은 문맥을 AI에게 제공한다.

Atlas가 추구하는 방향과 상당히 비슷하다.

---

# 6. ProcFunc

논문인데 굉장히 인상적이다.

Python 함수로

```
create_wall()

create_window()

create_room()
```

같은 식으로

절차적 모델링을 한다.

### 내가 하나 추천하고 싶은 조사 대상

다음으로는 **"Blender 기반 Procedural Generator"** 프로젝트들을 깊게 살펴보는 걸 추천해.

예를 들면:

- BlenderProc
- ProcFunc
- Geometry Nodes 기반 생성기
- AI + Geometry Nodes 결합 프로젝트

이 분야는 **Exelion Forge의 핵심 기술과 가장 많이 겹치는 영역**이라, 아키텍처나 코드 구조에서 참고할 만한 아이디어를 많이 얻을 수 있을 거야.

이야... 깃을 이용해서 학습도 했겠다.

맞아. 이 부분이 꽤 중요한 포인트야. 지금 네가 발견한 흐름은 사실 **Atlas의 방향과 상당히 맞닿아 있어.**

예전에는 Git을 단순히:

> "코드 저장소"

라고 생각했는데, AI 시대에는 좀 달라졌어.

GitHub 자체가 거대한 **개발 지식 데이터베이스** 역할을 하고 있어.

---

예를 들어 네가 찾은 Blender 관련 프로젝트들을 보면:

```
GitHub Repository

├── README.md
├── docs/
├── scripts/
├── assets/
│   ├── .blend
│   ├── texture
│   └── animation
├── examples/
└── tests/
```

이 구조 자체가 하나의 "학습 자료"야.

AI 입장에서는 단순히 코드만 보는 게 아니라:

- 왜 이렇게 설계했는지
- 어떤 폴더 구조를 쓰는지
- 어떤 이름 규칙을 쓰는지
- 어떤 자동화 방식을 쓰는지
- 실제 사용 예제는 무엇인지

까지 볼 수 있어.

---

네가 Atlas에서 만든 방식과 연결하면 재미있는 구조가 돼.

기존 방식:

```
사람
 ↓
검색
 ↓
자료 읽기
 ↓
코딩
```

AI 시대:

```
GitHub
 ↓
AI 분석
 ↓
패턴 추출
 ↓
내 프로젝트 구조에 적용
 ↓
자동 개선
```

---

특히 Exelion Forge는 이런 공개 프로젝트들의 "조합"에 가까워 보여.

예를 들면:

### BlenderForge 계열

→ AI가 Blender 조작

### MB-Lab 계열

→ 파라미터 기반 캐릭터 생성

### BlenderProc 계열

→ 절차적 생성

### Motion Generation 계열

→ 애니메이션 생성

### 네가 만든 Atlas

→ 프로젝트 관리, 목표, 상태, 에이전트 관리

---

결국 네가 만들려는 건:

```
AI Game Studio OS

          Atlas
            |
     +------+------+
     |             |
 Exelion Forge    Coin-S
     |
 Blender Pipeline
     |
Character Generator
     |

```

이런 형태에 가까워.

---

그리고 한 가지 더 재미있는 점.

네가 전에 말했던:

> "AI는 모든 대화를 기억하지 못하니까 문서화해야 한다"

이것과 GitHub 방식은 같은 원리야.

AI에게 중요한 것은 **기억(memory)**이 아니라 **검색 가능한 지식 구조(context)**야.

그래서:

- README
- ARCHITECTURE.md
- DESIGN.md
- TASK.md
- CHANGELOG

이런 문서가 결국 AI의 "장기 기억" 역할을 한다.

---

솔직히 말하면 지금 네가 하는 방식은 일반적인 1인 게임 개발 방식보다 조금 다르다.

보통은:

```
모델링 → 코드 → 게임
```

인데,

너는:

```
지식 저장소
    ↓
AI 에이전트
    ↓
자동 생성 시스템
    ↓
게임
```

쪽으로 가고 있어.

그래서 GitHub에서 Blender 파일을 찾은 것도 단순히 에셋을 구하는 관점보다, **"다른 사람이 만든 제작 시스템을 분석하는 관점"**으로 보는 게 훨씬 가치가 있어 보여.

급할수록 돌아가는게 맞아

맞아. 지금 상황에서는 그 말이 꽤 정확한 방향이라고 생각해.

특히 **Exelion + Atlas** 같은 규모에서는 "빨리 게임 하나 만들자"로 들어가면 오히려 나중에 막힐 가능성이 커 보여.

예를 들면:

```
급하게 제작
 ↓
캐릭터 하나 완성
 ↓
두 번째 캐릭터 필요
 ↓
처음부터 다시 제작
 ↓
애니메이션 관리 지옥
 ↓
에셋 관리 지옥
```

이 흐름이 1인 개발에서 가장 흔한 함정이야.

반대로 지금처럼 기반을 만들면:

```
Blender 구조 연구
 ↓
생성 규칙 정리
 ↓
Python 자동화
 ↓
파라미터화
 ↓
캐릭터 생성기
 ↓
여러 캐릭터 생산
```

으로 바뀐다.

---

특히 네 경우는 일반적인 게임 개발과 조금 다른 점이 있어.

Exelion은 단순히 "게임 하나"가 아니라:

- 메카 디자인
- 캐릭터
- 3D 프린팅 가능 모델
- 게임 에셋
- IP 확장

까지 염두에 두고 있잖아.

그러면 처음 만든 모델이 버려지는 게 아니라 **생산 시스템의 첫 번째 결과물**이 되어야 해.

---

지금 GitHub를 보는 것도 같은 맥락이라고 봐.

단순히:

> "남이 만든 모델 가져오자"

가 아니라,

> "남들이 어떻게 반복 가능한 제작 시스템을 만들었는지 배우자"

에 가까워.
