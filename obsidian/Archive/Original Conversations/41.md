네, 그럴 가능성이 꽤 큽니다.

특히 Cline 같은 **에이전트형 AI**는 일반 챗봇과 달리 실제로 파일을 읽고, 검색하고, 수정하는 행동을 해야 합니다. 목표가 너무 넓으면 스스로 "어디서부터 시작해야 하지?"를 결정하려고 하다가 같은 행동을 반복하며 실패하는 경우가 있습니다.

예를 들어,

> "Atlas의 문서를 검토해."

라고 하면 Cline 입장에서는 다음과 같은 문제가 생깁니다.

- 문서가 몇 개인지 모름
- 어디까지가 '문서'인지 모름
- 읽기 순서를 모름
- 산출물이 무엇인지 모름
- 언제 작업이 끝난 것으로 판단해야 하는지 모름

그러면 README를 읽고 → 다른 문서를 찾고 → 또 찾고 → 계속 탐색하다가 동일한 도구 호출을 반복하게 될 수 있습니다.

반대로 이렇게 나누면 훨씬 안정적입니다.

### 1단계

> README.md, VISION.md, ARCHITECTURE.md만 읽고 프로젝트 구조를 요약해.

### 2단계

> 나머지 Markdown 문서를 모두 찾아 목록을 작성해.

### 3단계

> 중복되거나 오래된 문서를 찾아.

### 4단계

> 코드와 문서를 비교해서 불일치만 보고해.

이처럼 **범위를 작게 나누면** 에이전트가 훨씬 잘 움직입니다.

---

마스터의 Atlas처럼 문서가 많은 프로젝트에서는 제가 권하는 방식은 **"탐색 → 분석 → 수정"의 3단계**입니다.

1. **탐색(Search)**: 어떤 문서가 있는지 파악.
2. **분석(Analyze)**: 문서 간 충돌이나 누락을 찾음.
3. **수정(Fix)**: 승인된 항목만 수정.

이렇게 하면 한 번에 많은 파일을 열려고 하다가 실패하는 일을 줄일 수 있습니다.

Atlas 정도 규모라면, 한 번에 모든 문서를 감사시키기보다 **문서를 10~20개 정도의 묶음으로 나눠 검토**시키는 것이 성공률과 결과 품질 모두 더 좋습니다.

coin-s, excelion, excelion-forge 이 개별 프로젝트의 문서를 정리하라는 프롬프트를 만들어줘

마스터의 프로젝트처럼 규모가 있는 경우에는 **'정리'를 명확한 작업으로 정의**하는 것이 중요합니다. 아래 프롬프트는 문서를 직접 삭제하지 않고, 구조를 분석하고 정리안을 제시한 뒤 필요한 문서는 갱신하도록 유도하는 형태입니다.

다음 프롬프트를 각 프로젝트(`coin-s`, `exelion`, `exelion-forge`)에 그대로 사용할 수 있습니다. 프로젝트 이름만 바꿔서 사용하면 됩니다.

# 프로젝트 문서 정리 작업

당신은 Atlas DevOS의 시니어 프로젝트 아키텍트이자 기술 문서 관리자입니다.

현재 프로젝트의 모든 Markdown 문서를 검토하여 문서 체계를 정리하세요.

## 목표

프로젝트 문서가 현재 구현 상태와 일치하도록 정리하고, 중복과 오래된 내용을 제거하여 유지보수하기 쉬운 문서 구조를 만드는 것이 목적입니다.

## 작업 절차

### 1. 문서 조사

프로젝트 내의 모든 Markdown(.md) 문서를 찾아 목록을 작성하세요.

각 문서에 대해 다음을 정리하세요.

- 파일 경로
- 문서 목적
- 마지막으로 참조되는 기능
- 현재 프로젝트에서의 필요성

---

### 2. 문서 분류

각 문서를 다음 중 하나로 분류하세요.

- Active (현재 사용)
- Needs Update (내용 수정 필요)
- Duplicate (중복)
- Deprecated (폐기 예정)
- Archive (보관)

분류 이유도 함께 작성하세요.

---

### 3. 내용 검토

다음을 확인하세요.

- 현재 코드와 일치하는가
- 구현되지 않은 기능을 설명하고 있는가
- 삭제된 기능을 설명하고 있는가
- 오래된 설계를 포함하는가
- 잘못된 경로나 파일명을 사용하는가
- 링크가 깨져 있는가

---

### 4. 문서 구조 개선

다음을 제안하세요.

- 병합해야 하는 문서
- 분리해야 하는 문서
- 새로 필요한 문서
- 삭제 가능한 문서

---

### 5. 문서 업데이트

Active 또는 Needs Update 문서는 현재 구현 상태에 맞게 수정하세요.

단,

- 의미를 임의로 변경하지 마세요.
- 구현되지 않은 기능을 추가하지 마세요.
- 추측으로 내용을 작성하지 마세요.

---

### 6. README 개선

README가 다음 내용을 포함하는지 확인하고 부족하면 보완하세요.

- 프로젝트 목적
- 주요 기능
- 디렉터리 구조
- 개발 환경
- 실행 방법
- 현재 진행 상태
- 관련 Atlas 프로젝트

---

### 7. 용어 통일

프로젝트 전체에서 동일한 용어를 사용하도록 수정하세요.

예)

- Goal
- Sprint
- Task
- Registry
- Agent
- Runtime
- Context

---

### 8. 최종 보고서 작성

작업이 끝나면 다음 형식으로 보고하세요.

# Documentation Cleanup Report

## Summary

- 총 문서 수
- 수정된 문서
- 신규 문서
- 삭제 후보
- 보관 문서

## 주요 변경 사항

변경 내용을 요약하세요.

## 남은 작업

향후 정리가 필요한 문서를 작성하세요.

## 작업 원칙

- 작은 단위로 수정하세요.
- 문서만 수정하고 코드에는 영향을 주지 마세요.
- 불확실한 내용은 TODO로 남기세요.
- 추측하지 말고 실제 프로젝트 상태를 기준으로 판단하세요.
- 변경 이유를 명확히 기록하세요.

이 프롬프트는 **한 프로젝트당 한 번씩 실행**하는 것을 권장합니다.

- `Atlas/projects/coin-s`에서 실행 → Coin-S 문서 정리
- `Atlas/projects/exelion`에서 실행 → Exelion 문서 정리
- `Atlas/projects/exelion-forge`에서 실행 → Exelion Forge 문서 정리

이렇게 프로젝트별로 분리하면 Cline이 한 번에 처리해야 할 범위가 줄어들어 반복 실패에 빠질 가능성도 크게 낮아집니다.

exelion은 오타야 excelion이 맞아 아틀라스 프로젝트의 .md와 .py, 그리고 디렉토리/파일이름에서 변경을 진행해줘 이거 프롬프트 만들어줘

이 작업은 **단순 문자열 치환이 아니라 리팩토링**에 가깝습니다. 그래서 "찾아서 바꿔"가 아니라 **영향 범위를 분석 → 변경 → 검증 → 보고**까지 포함하는 프롬프트가 안전합니다.

# Atlas 프로젝트 명칭 변경 리팩토링

당신은 Atlas DevOS의 시니어 소프트웨어 아키텍트입니다.

현재 프로젝트에는 프로젝트명이 잘못 표기되어 있습니다.

기존 명칭

```
Exelion
exelion
EXELION
```

를

```
Excelion
excelion
EXCELION
```

으로 변경하세요.

## 변경 대상

다음 항목을 모두 검사하세요.

### 1. Markdown

- 모든 *.md

### 2. Python

- 모든 *.py

### 3. 디렉터리

디렉터리 이름에 exelion이 포함되어 있으면 변경하세요.

예)

```
projects/exelion
→
projects/excelion
```

### 4. 파일명

파일명에 exelion이 포함되어 있으면 변경하세요.

예)

```
EXCELION_GUIDE.md
```

- 로그 메시지
- CLI 출력
- 예제 코드

- 상대경로
- 이미지 링크
- 문서 참조

- TOML
- INI
- GitHub Actions

- 환경설정 파일
