## Atlas 기준 최종 구조

제가 보기에는 Atlas는 다음 4층 구조가 적합합니다.

```
Atlas Knowledge System

1. Raw Memory
   └─ conversations/raw
      (대화 원본)

2. Project Knowledge
   └─ conversations/{project}
      (프로젝트별 정리)

3. Engineering Knowledge
   └─ architecture
      decisions
      lessons

4. Permanent Decisions
   └─ ADR
      (변경 불가능한 기준)
```

이렇게 구성하면 나중에 Sera가 Atlas 저장소를 읽을 때:

- "무슨 일이 있었나?" → conversations
- "왜 이렇게 결정했나?" → ADR
- "현재 구조는?" → architecture
- "과거 실패 사례는?" → lessons

로 바로 접근할 수 있습니다.

현재까지의 대화 기록 중에서는 특히 **Sera ↔ Forge 관계 변경**, **Atlas가 Root가 된 구조 변경**, **AI Provider Architecture**, **Forge 개발 방향 변경**은 ADR 후보로 분류하는 것이 좋겠습니다.

마스터, 지금까지의 대화 흐름을 기준으로 **Atlas 메인 저장소에 바로 넣을 수 있는 문서 구조와 초기 문서 목록**으로 정리하겠습니다.

기준은 다음으로 잡겠습니다.

- **Atlas = 최상위 관리 저장소**
- **Sera = AI 개발 플랫폼**
- **EXCELION Forge = Sera 위에서 개발되는 제작 시스템**
- **게임 EXCELION = Forge가 지원하는 최종 프로젝트**
- 대화 기록은 단순 로그가 아니라 **의사결정 근거 데이터**로 관리

```
# Purpose

Atlas 프로젝트 개발 과정에서 얻은 경험과

# 1. AI Agent 개발 지원의 한계


## Situation

Continue + Local LLM 환경에서
코드 분석 및 수정 작업을 진행했다.

사용 모델:

- Qwen3-Coder
- Ollama Local Runtime


## Problem

AI Agent가:

- 존재하지 않는 파일을 기반으로 판단
- 프로젝트 전체 Context 부족
- 이전 대화 기억 손실
- 수정 완료 여부 검증 부족

문제를 보였다.


## Lesson

AI Agent에게는:

"코드를 수정하는 능력"

보다 먼저

"현재 상태를 정확히 파악하는 능력"

이 필요하다.


## Principle

작업 전 필수 단계:

1. Repository 상태 확인
2. 파일 존재 확인
3. 실행 환경 확인
4. 변경 범위 확인


---

# 2. Context 유지의 중요성


## Situation

긴 대화 과정에서:

- 설계 변경
- 문제 해결
- 방향 전환

이 반복되었다.


## Problem

대화 Context가 유지되지 않을 경우:

- 이전 결정과 충돌
- 같은 작업 반복
- 설계 의도 손실


## Lesson

중요한 결정은 반드시 문서화해야 한다.


## Principle

대화:

Temporary Memory


문서:

Permanent Memory


따라서:

"대화가 끝나기 전에 지식을 저장한다."


---

# 3. Validate Active Rig 문제


## Situation

EXCELION Forge 개발 중
Validate Active Rig 기능 오류 발생.


## Problem

여러 차례 오류 내용을 전달했지만
수정 완료 검증이 되지 않았다.


원인:

- 실행 환경 확인 부족
- 실제 코드 위치 확인 부족
- 테스트 절차 부족


## Lesson

AI 수정 결과는 반드시 실행 검증해야 한다.


## Principle

수정 완료 기준:

1. 코드 변경
2. 실행 테스트
```

오히려 지금까지의 흐름을 보면 **마스터가 해야 하는 역할과 AI가 해야 하는 역할을 구분해 가는 과정**이라고 보는 게 맞습니다.

그리고 한 가지 짚고 싶은 게 있습니다.

지금 마스터가 한 일은 "문서를 잘 쓰는 능력"이나 "아키텍처 전문가 능력"과는 조금 다른 종류의 능력입니다.

처음부터 완성된 구조를 설계한 게 아니라:

- Forge를 만들다가
- SERA의 필요성을 발견하고
- AI Agent의 한계를 경험하고
- 문서화의 중요성을 깨닫고
- 결국 ATLAS라는 상위 구조까지 정리했다

이 흐름 자체가 **시스템 설계 과정**입니다.

물론 세부적인 UML을 그리거나, 완벽한 아키텍처 문서를 쓰는 일은 AI가 잘 도울 수 있습니다. 하지만:

> "무엇이 문제인가?"
> 
> "어떤 역할이 필요한가?"
> 
> "왜 기존 방식이 한계가 있는가?"

를 찾아내는 것은 사람이 해야 하는 부분입니다.

입니다.

그리고 재미있는 점은, 마스터가 "나는 그런 역량이 안 된다"고 느끼는 부분이 사실 **AI 시대에 가장 필요한 역할**일 가능성이 높습니다.

예전에는:

> 내가 모든 것을 알아야 개발 가능

이었다면,

지금은:

> 내가 무엇을 만들고 싶은지 명확히 하고, AI들이 제대로 움직이도록 방향을 잡는다

쪽으로 바뀌고 있습니다.

지금 프로젝트 규모는 개인이 머릿속으로 관리하기에는 이미 커졌습니다.

지금 당장은 SERA가 없어서 마스터가 ATLAS 역할까지 일부 맡고 있는 상태라고 보면 됩니다. SERA가 합류하면 그 부담을 넘기는 구조가 되는 거고요.

그리고 솔직히 말하면, 지금까지 대화에서 가장 중요한 건 코드 한 줄보다 **"우리가 어떤 구조로 AI와 함께 개발할 것인가"라는 운영 체계를 찾아낸 것**이라고 봅니다. 이 부분이 잡혀야 Forge든 EXCELION이든 계속 갈 수 있습니다.포지가 기능적으로 필요한 부분과 각 기능을 어떻게 구현할지 논의해보자

- SQLite
- JSON metadata

- Blender Python API
- bpy
- subprocess

- Conversation State
- 진행률
- Audit Result
- Cache
- Working Memory
- Todo
- Active Context

특징

- 계속 변함
- 세션마다 달라짐
- 실행 중 생성
- 종료되면 일부만 남음

즉,

> **Atlas의 신경계(Nervous System)**

입니다.

---

## 왜 분리해야 하는가?

예를 들어 AI가 작업 중이라고 해보겠습니다.

잘못된 구조라면

```
Goal
 ↓
Conversation
 ↓
Task
 ↓
Rule 수정
 ↓
Goal 변경
```

실행 과정에서 Rule이나 Goal이 오염될 수 있습니다.

반대로 분리하면

```
Knowledge
 ├─ Goal
 ├─ Rule
 ├─ Workflow
 └─ Sprint

↓

Runtime

 ├─ Current Task
 ├─ State
 ├─ Memory
 └─ Audit
```

Runtime는 Knowledge를 **읽기만** 합니다.

Knowledge는 Runtime 때문에 바뀌지 않습니다.

---

## 이것이 가져오는 효과

### 1. 재현성 (Reproducibility)

같은 Goal이면

항상 같은 Rule을 읽습니다.

---

### 2. 안정성 (Stability)

실행 중 버그가 생겨도

Knowledge는 손상되지 않습니다.

---

### 3. 감사 가능성 (Auditability)

감사 시

```
Knowledge Version
↓

Runtime Log
↓

Output
```

를 추적하면 됩니다.

---

### 4. 여러 Runtime 동시 실행

예를 들어

```
Knowledge
    │
 ┌──┴──────┐
 │         │
GPT Runtime
 │
Claude Runtime
 │
Qwen Runtime
```

모든 Runtime이

동일한 Rule을 공유하면서

각자의 State만 따로 유지할 수 있습니다.

---

### 5. 운영 확장성

미래에는

```
Knowledge Repository

↓

Atlas Runtime A
Atlas Runtime B
Atlas Runtime C
Atlas Runtime D
```

처럼 여러 에이전트가 하나의 지식 저장소를 공유하는 구조도 가능합니다.

## Atlas에서의 의미

이 원칙은 Atlas를 단순한 프롬프트 모음이 아니라 **운영체제(OS)처럼 동작하는 플랫폼**으로 만드는 기반입니다.

- **Knowledge Layer**는 정책, 목표, 규칙, 워크플로를 정의하는 **불변에 가까운 기준 저장소**입니다.
- **Runtime Layer**는 그 기준을 읽어 실제 작업을 수행하고 상태를 관리하는 **가변 실행 환경**입니다.
- Runtime은 Knowledge를 참조하지만 직접 수정하지 않으며, Knowledge의 변경은 별도의 검토·승인 절차를 통해 이루어집니다.

이러한 분리를 유지하면 동일한 지식 기반 위에서 GPT, Claude, Qwen 등 서로 다른 LLM Runtime을 교체하거나 병행 운용하더라도 일관된 동작 원칙과 감사 가능성을 확보할 수 있습니다.

마스터, 직전 내용까지 합쳐서 보면 **이번 작업지시는 단순히 `atlas_verify_engine.py`를 다시 만들라는 지시가 아니어야 합니다.** 핵심은 두 가지를 동시에 바로잡는 겁니다.

1. **실제 Repository에 필요한 문서와 구현물을 생성·검증할 것**
2. **에이전트가 Repository에 접근하고 작업한 결과를 증거로 남길 수 있도록 인터페이스 자체를 수정할 것**

그리고 가장 중요한 건, **작업지시문 안에서 "이미 생성했다"거나 "완료됐다"고 전제하지 않는 것**입니다. 이전 요약에는 실제 Repository와 맞지 않는 완료 주장이 섞여 있었으므로, 이번에는 Qwen이 먼저 현재 상태를 다시 확인하게 해야 합니다.

제가 보기엔 아래 작업지시가 가장 적절합니다.

# ATLAS-VERIFY-006: Repository Interface Repair & Evidence-Grounded Framework Reconstruction

## 1. 작업 목적

이번 작업의 목적은 Atlas의 현재 상태를 **Repository Evidence를 기준으로 재정립하고**, 이전 작업 과정에서 발생한 **Agent Claim과 실제 Repository 상태 간의 불일치​**를 해결하는 것이다.

이번 작업에서는 다음 두 문제를 동시에 해결한다.

1. **Repository Interface 문제**
    - AI Agent가 실제 Repository의 파일을 생성·수정·읽기·실행·검증할 수 있는지 명확히 확인한다.
    - Agent가 작업을 수행했다고 주장하는 것과 실제 파일 시스템에 작업이 반영된 것을 구분한다.
    - 작업 결과를 Repository Evidence로 확인할 수 있는 운영 절차를 구축한다.
2. **Atlas Framework Artifact 문제**
    - 현재 Repository에 실제로 존재하는 Atlas 관련 문서를 먼저 조사한다.
    - 이전 대화에서 존재한다고 주장되었지만 실제 Repository에서 확인되지 않은 문서는 다시 생성한다.
    - 필요한 핵심 Framework 문서가 실제 Repository에 존재하도록 만든다.
    - 생성한 문서는 반드시 다시 읽고 내용과 상호참조를 검증한다.

# 2. 절대 규칙: Evidence-Grounded Operation

이번 작업의 모든 판단은 다음 규칙을 따른다.

> **Agent Claim은 Repository Evidence가 아니다.**

- "검증됐다"
- "CLOSED다"
- "Self-Description이 가능하다"
- "Vocabulary Closure가 확인됐다"

대신 각 항목을 다음 상태로 분류한다.

- `EXISTS`
- `CREATED`
- `MODIFIED`
- `READ_VERIFIED`
- `EXECUTED`
- `TESTED`
- `VERIFIED`
- `UNVERIFIED`
- `MISSING`

상태는 반드시 실제 작업 결과에 근거하여 결정한다.

# 8. Phase 5 — Development Verification과 System Verification 분리

Atlas 검증을 두 계층으로 명확히 분리한다.

## Layer A — Development Verification

다음을 검증한다.

- 파일이 실제로 존재하는가?
- 파일이 실제로 생성되었는가?
- 파일 내용이 실제로 존재하는가?
- 수정 내용이 실제로 반영되었는가?
- 실행이 실제로 수행되었는가?
- 테스트가 실제로 실행되었는가?
- 실행 결과가 무엇인가?

## Layer B — System Verification

다음을 검증한다.

- Atlas 문법이 일관적인가?
- Canonical Vocabulary가 닫혀 있는가?
- Ontology가 일관적인가?
- Type System이 일관적인가?
- Logical Framework가 일관적인가?
- Self-Description이 가능한가?
- Circular Dependency가 존재하는가?
- 실제 Artifact가 Atlas Language로 표현 가능한가?

두 계층의 결과를 절대로 혼합하지 않는다.

예:

```
Development Verification:
atlas_verify_engine.py EXISTS = TRUE

System Verification:
Closed Formal Language = UNPROVEN
```

파일이 존재한다는 사실만으로 시스템이 검증됐다고 판단하지 않는다.

# 13. 절대 금지 사항

다음 행동을 금지한다.

1. 파일을 실제로 생성하지 않고 생성했다고 주장하지 않는다.
2. 파일을 실제로 읽지 않고 내용을 알고 있다고 주장하지 않는다.
3. 테스트를 실행하지 않고 통과했다고 주장하지 않는다.
4. 존재하지 않는 파일을 존재한다고 보고하지 않는다.
5. Agent의 이전 응답을 Repository Evidence로 취급하지 않는다.
6. 실패한 검증을 조용히 수정하여 성공으로 만들지 않는다.
7. 검증 결과를 임의로 CLOSED로 승격하지 않는다.
8. Self-Description이 가능하다는 설계만으로 실제 Self-Description 검증 완료라고 주장하지 않는다.
9. Vocabulary Closure가 설계되어 있다는 사실만으로 Vocabulary Closure가 증명됐다고 주장하지 않는다.
10. 구현 완료와 검증 완료를 동일하게 취급하지 않는다.

# 14. 최종 목표

이번 작업의 목표는 "Atlas가 CLOSED임을 증명하는 것"이 아니다.

이번 작업의 진짜 목표는 다음과 같다.

> **Atlas의 실제 Repository 상태와 Agent의 작업 결과 사이에 존재하는 인터페이스 및 증거 공백을 제거하고, 실제 존재하는 Artifact를 기반으로 Atlas의 현재 상태를 정확하게 판정할 수 있는 기반을 구축하는 것.**

따라서 최종 결과가 다음 중 어느 것이든 허용한다.

- `VERIFIED`
- `PARTIALLY_VERIFIED`
- `UNPROVEN`
- `INCONSISTENT`
- `BLOCKED`

중요한 것은 결과 자체가 아니라 **각 결과를 뒷받침하는 실제 Repository Evidence를 제시하는 것**이다.

# 2. Non-Negotiable Evidence Rule

모든 결과는 다음 상태를 엄격히 구분한다.

- `CLAIMED`
- `MISSING`
- `CREATED`
- `MODIFIED`
- `EXECUTED`
- `TESTED`
- `VERIFIED`
- `UNVERIFIED`
- `FAILED`
- `BLOCKED`

특히 다음을 금지한다.

1. 실제 파일을 확인하지 않고 `EXISTS`라고 보고하지 않는다.
2. 실제 실행하지 않고 `EXECUTED`라고 보고하지 않는다.
3. 실제 테스트하지 않고 `TESTED`라고 보고하지 않는다.
4. 검증 대상 전체를 검사하지 않고 `VERIFIED`라고 보고하지 않는다.
5. `CLOSED`, `SELF-DESCRIPTIVE`, `VOCABULARY-CLOSED` 등의 결론을 실행 Evidence 없이 선언하지 않는다.
6. 이전 Agent 응답에 등장한 파일이나 구현을 실제 Repository에 존재하는 것으로 간주하지 않는다.

# 13. 가장 중요한 작업 원칙

이번 작업의 성공 기준은 "많은 코드를 작성하는 것"이 아니다.

**실제 Repository와 Agent의 작업 상태가 일치하는지를 증명하는 것**이다.

따라서 다음 문장을 작업 전체의 기준으로 삼아라.

> **Do not report what you intended to do.**
> 
> **Do not report what you generated in memory.**
> 
> **Report only what exists, what was executed, and what was evidenced.**

이번 작업에서 이전 Claim과 실제 Repository 사이에 차이가 발견되더라도 이를 실패로 숨기지 마라.

오히려 그 차이를 정확히 기록하고 복구하는 것이 이번 작업의 핵심이다.

최종적으로 Atlas가 검증해야 할 대상은 두 가지다.

1. **Atlas System이 올바른가?**
2. **Atlas를 만드는 과정 자체가 Evidence-Grounded한가?**

두 검증을 분리해서 수행하고, 어느 한쪽의 결과를 다른 쪽의 증거로 사용하지 마라.

이 작업지시가 지금까지의 흐름을 가장 잘 이어갑니다.

특히 이번에는 **"문서를 만들어라"만 시키면 안 됩니다.** `생성 → 존재 확인 → 다시 읽기 → 실행 → 테스트 → 결과 보고`까지 한 사이클을 강제해야 합니다. 그래야 지난번처럼 Qwen이 메모리상에서 코드를 작성한 뒤 실제 Repository에 반영됐다고 착각하는 문제가 다시 생기지 않습니다.

그리고 한 가지 더 중요한 점이 있습니다. **`CLOSED`를 목표로 하되, CLOSED를 미리 정답으로 정해놓으면 안 됩니다.** 이번 작업의 진짜 성공은 CLOSED가 나오는 것이 아니라, **CLOSED든 UNPROVEN이든 실제 Repository가 말하는 결과를 그대로 받아들이는 것**입니다.포지가 어떻게. 개발되어야. 하지? 애드온 별도 어플리케이션. 하이브리드?

마스터, 지금까지 EXCELION Forge의 방향을 보면 **단순 Blender 애드온으로 끝내면 안 되고, 완전한 별도 어플리케이션으로 가도 비효율적**이라고 봅니다.

가장 적합한 형태는 **하이브리드 아키텍처**입니다.

정확히 말하면:

> **Forge = 독립 제작 플랫폼**
> 
> **Blender Add-on = Forge의 실행 에이전트(Worker)**

구조로 가는 것이 좋습니다.

## 1. 현재 원격 저장소 확인

터미널에서:

```
git remote -v
```

결과 확인.

예:

```
origin https://github.com/xxxxx/Atlas.git
```

여기가 웹에서 보고 있는 저장소와 같은지 확인.

---

## 2. 현재 브랜치 확인

```
git branch
```

예:

```
* main
```

또는:

```
git branch -a
```

원격 브랜치 확인.

흔한 경우:

```
main
origin/main
origin/dev
```

인데 웹에서는 `main`을 보고 있고 실제 푸시는 `dev`에 된 경우.

---

## 3. 마지막 커밋이 원격에 있는지 확인

```
git log --oneline -5
```

그리고:

```
git log origin/main --oneline -5
```

비교.

마지막 커밋 ID가 같아야 한다.

---

## 4. push 결과 다시 확인

```
git status
```

정상이라면:

```
Your branch is up to date with 'origin/main'
nothing to commit, working tree clean
```

비슷하게 나와야 함.

---

## 5. GitHub 웹에서 확인할 부분

웹 저장소 화면에서:

- Branch 선택 확인 (`main`, `master`, `dev`)
- Commits 탭 확인
- 새로고침

특히 GitHub는 기본 브랜치가 다르면 파일 화면에서 바로 안 보일 수 있어.

---

지금 네가 작업했던 흐름을 보면 가능성이 높은 건:

1. **WSL 경로와 Windows Git 저장소가 다름**
2. **다른 브랜치에 push**
3. **다른 remote 저장소**

이 세 가지야.

우선 이 세 명령 결과를 보여줘:

```
git remote -v
git branch -vv
git status
```

그러면 바로 어디로 갔는지 확인 가능해.

웝에서 안 보이면 반영이 안 된거지?

꼭 그렇지는 않아.

**웹에서 안 보인다 = push가 안 됐다**는 의미는 아니야. 몇 가지 경우가 있어.

가능성 순서대로 보면:

1. **다른 브랜치를 보고 있음 (가장 흔함)**  
    예:
    
    ```
    push → feature/forge-task
    웹 → main 보고 있음
    ```
    
    그러면 웹 파일 화면에는 안 보일 수 있어.
    
2. **다른 저장소에 push 됨**
    
    ```
    git remote -v
    ```
    
    의 주소와 웹에서 보고 있는 저장소가 다르면 당연히 안 보임.
    
3. **웹 화면 캐시/표시 문제**  
    드물지만 새로고침 후 보이는 경우도 있음.
4. **실제로 push 안 됨**  
    이 경우도 가능하지만, `git push`가 오류 없이 끝났다면 가능성은 낮아.

---

가장 확실한 확인 방법은:

```
git status
```

그리고:

```
git log --oneline --decorate -5
```

여기서 마지막 커밋에:

```
origin/main
```

같은 표시가 붙어 있으면 원격에 올라간 상태야.

예:

```
abc1234 (HEAD -> main, origin/main) Add Forge mission document
```

이면 웹에도 있어야 해.

만약:

```
abc1234 (HEAD -> main) Add Forge mission document
def5678 (origin/main)
```

이면 로컬에만 있고 push가 안 된 상태.

---

네 경우는 아까 Atlas에서 작업하던 흐름을 보면 **WSL 환경에서 Git 작업하고 웹은 다른 브랜치를 보고 있는 경우**가 꽤 가능성이 있어.

아래 세 개만 보면 바로 판단 가능해.

```
git branch -vv
git remote -v
git log --oneline -3
```

결과를 보면 된다.

좋은 질문이야. GitHub는 겉으로 보면 "무료 저장소 서비스"처럼 보이지만, 실제 비즈니스 모델은 꽤 명확해.

핵심은 **개발자의 무료 사용자를 확보하고, 기업에게 돈을 받는 구조**야.

# 프로젝트 개요

EXCELION Forge는 완성된 게임이나 단순한 3D 모델 생성기가 아니다.

현재 목표는 **EXCELION 게임 개발을 위한 Blender 기반 제작 및 검증 시스템(Development Pipeline)** 을 구축하는 것이다.

Forge는 향후 캐릭터, 리깅, 애니메이션, 검증을 자동화하는 제작 플랫폼으로 발전한다.

---

# 현재 프로젝트 위치

현재 Forge는 초기 개발 단계이며 핵심은 다음과 같다.

- Blender Add-on 기반 제작 환경
- Rig 검증 시스템
- 제작 파이프라인 자동화
- AI Agent와 연동 가능한 구조
- 문서 기반 개발

아직 완전한 캐릭터 생성기나 게임 제작 툴은 아니다.

---

# 프로젝트 목표

Forge는 다음과 같은 제작 과정을 자동화하는 것을 목표로 한다.

1. 캐릭터 생성
2. 리깅
3. 애니메이션 준비
4. 구조 검증
5. EXCELION에서 사용할 데이터 생성

Forge 개발 시 다음 원칙을 유지한다.

- 문서 우선(Document First)
- 증거 기반 개발(Evidence Based)
- Zero Hallucination
- Runtime 상태 관리
- 모든 작업은 재현 가능해야 함

---

```
 ├── Character Pipeline
 ├── Runtime
 ├── Documents
 └── AI Agent
```

# 확인된 문제

## Validate Active Rig

프로젝트에서 반복적으로 발생한 문제

증상

- Validate Active Rig 실행 시 Runtime Error 발생
- AI가 수정했다고 보고했지만 실제 해결되지 않음
- 동일 문제가 여러 차례 재발

이 기능은 현재 Forge의 핵심 안정화 대상이다.

# AI Agent 운영 방식

Forge는 AI Agent를 활용한 개발을 전제로 한다.

요구사항

- 허위 보고 금지
- 실행 결과와 증거 제시
- 문서 확인 후 작업
- 실제 수정 여부 검증
- Runtime 상태 기록

# 프로젝트 변경 사항

초기에는 Forge 내부에서 SERA를 개발하는 방향이었다.

현재는 방향이 변경되었다.

**SERA를 먼저 개발하고, 이후 SERA를 이용하여 Forge를 개발하는 구조​**로 전환되었다.

이 변경으로 Forge 개발은 일시적으로 후순위가 되었으며, SERA 완성 이후 Forge 개발을 가속화하는 전략을 채택하였다.

2. SERA 안정화
3. Forge 개발 재개
4. Character Pipeline 구축
5. EXCELION 제작 자동화

# 장기 목표

Forge는 최종적으로 EXCELION 제작을 위한 통합 제작 시스템이 되는 것을 목표로 한다.

최종 비전은 다음 기능을 하나의 플랫폼에서 제공하는 것이다.

- 캐릭터 제작
- 리깅
- 애니메이션
- 검증
- 데이터 생성
- AI 기반 제작 지원
- EXCELION 게임 개발 자동화

이 문서는 **현재 프로젝트 대화에서 확인된 Forge 관련 내용만** 정리한 기준선(Baseline)입니다. 이후에는 이를 `FORGE_BASELINE.md`로 두고, 아키텍처·런타임·검증 시스템·캐릭터 파이프라인 등을 별도 문서로 분리하면 관리하기 훨씬 수월합니다.여기 대화기록을 Atlas 메인 저장소에서 관리할 예정입니다. 프로젝트별 docs 폴더에 들어갈 수 있는 구조로 작성해 주세요.

마스터, 이 대화는 **Atlas 메인 저장소에서 프로젝트별 docs로 관리**하는 목적이라면 단순 대화 로그보다는 "의사결정 기록 + 설계 자료 + 작업 지침" 형태로 변환하는 것이 좋습니다.

## 추가로 추천하는 파일

대화가 계속 쌓이면:

```
docs/conversation_archive/
```

를 만들고 원본 대화 요약을 보관하는 것도 좋습니다.

예:

```
conversation_archive/
├─ 20260725/
│  ├─ atlas_structure.md
│  ├─ local_llm_strategy.md
│  └─ project_management.md
```

다만 **원본 대화 전체 저장은 비추천**입니다.  
Atlas의 목적이 "대화를 저장하는 시스템"이 아니라 "대화에서 지식을 추출해 개발 시스템으로 만드는 것"이기 때문입니다.

현재 마스터가 만들고 있는 구조라면:

**대화 → 정리 → ADR/Design Doc → 프로젝트 docs → 코드/작업**

이 흐름이 가장 맞습니다.

네 반영해주세요.

마스터, 반영 방향으로 정리했습니다. 다만 현재 대화 환경에서는 Atlas 저장소 파일에 직접 커밋하거나 수정할 수는 없어서, **Atlas 메인 저장소에 적용할 문서 구조와 추가 내용을 기준안으로 확정**하는 형태로 반영하겠습니다.

적용 대상:

```
Atlas/
└─ docs/
   ├─ workflows/
   │  └─ DOCUMENT_SYNC_WORKFLOW.md   ← 추가
   │
   ├─ decisions/
   │  └─ ADR-0001-project-document-management.md   ← 추가
   │
   ├─ conversation_archive/
   │  └─ YYYYMMDD/
   │      └─ conversation_summary.md
   │
   └─ projects/
       ├─ excelion/
       │  └─ conversation/
       │
       ├─ excelion-forge/
       │  └─ conversation/
       │
       ├─ coin-s/
       │  └─ conversation/
       │
       └─ sera/
          └─ conversation/
```

````
## 프로젝트 개요

Exelion Forge는 Exelion 프로젝트의 개발을 지원하는 제작 시스템이다.
````

### 현재 정리된 범위

이 문서는 **이 프로젝트 대화에서 나온 내용만** 기반으로 정리한 것입니다. 다만 이전 대화들을 보면 Exelion Forge에 대해 더 구체적인 내용(Blender 애드온 구조, 생성 파이프라인, AI 모션, 에셋 생성기, 파라미터 시스템 등)이 많이 논의되었습니다.

그 내용까지 포함하면 `README.md` 수준이 아니라 다음과 같은 문서 세트로 확장할 수 있습니다.

- `README.md` — 프로젝트 소개
- `ARCHITECTURE.md` — Forge 시스템 구조
- `PIPELINE.md` — 제작 파이프라인
- `CHARACTER_GENERATOR.md` — 캐릭터 생성기 설계
- `ANIMATION.md` — AI 애니메이션 생성
- `ROADMAP.md` — 개발 로드맵

이렇게 구성하면 **Atlas 프로젝트 문서 수준**으로 체계적인 Exelion Forge 문서 세트를 만들 수 있습니다.
